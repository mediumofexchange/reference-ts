## 2026-09-20 — Resolve the complete shared scope before intrinsic exclusion

**Choice:** extend conditional §9.1 exclusion to non-opening shared-scope
checkpoints with no adopted block. Reuse the existing scope classifier's complete
dependency walk and the existing exact target fault record. Existing
[§9.1 at 183c09f](https://github.com/mediumofexchange/money-from-first-principles/blob/183c09f/pool-v3.md#91-compact-intrinsic-exclusion)
already requires every scoped snapshot, term, canonical predecessor and applicable
clock; no normative amendment or new evidence layout is needed.

**Reasoning:** the scope classifier resolves all scoped record views and parents,
the valid opening, each silence clock, a common last valid continuation, complete
directory carriage and matching segment/history/evidence hashes before consuming
an intrinsic failure. Its checkpoint cache binds the held signed commitment;
fault facts additionally bind its record index and segment. A fault authenticated
through either sibling snapshot can exclude the whole checkpoint because the
shared evidence hash must agree. Issuance authorization still uses the statement's
backing K from authenticated terms, regardless of selection or certificate backing.
Passing that checkpoint supplies no state and cannot replace either side of a
split/rejoin dependency. Known noncanonical continuation contexts still require
ordinary evidence; the compact exception does not bypass the continuity guard.

**Alternatives and costs:** keeping the one-backing restriction would preserve a
smaller supported subset, but require the faulty target's full event trail after
all scoped dependencies were already resolved. Adding a second scope certificate
or separate classifier would duplicate existing authenticated data and rules.
Remove only the one-backing guard; retain non-opening, lapse and empty-block
prerequisites. Work is bounded by the existing scope/checkpoint/event budgets;
compact records keep their existing byte/item/suffix bounds. No new signature,
primitive, key, configuration authority, wire field or runtime path is introduced.

**Falsifiers:** accepting an unknown sibling clock/state, using selection K for a
different backing's issue, ignoring a mismatched sibling snapshot, restoring a
spent split ancestor, or letting a cached exclusion bypass a dependency rejects
this choice. Design review found the existing guards sufficient. Integrated
adversarial review found no blocker and independently probed faulty selections,
unknown verifier results, repaired-commitment isolation and corrupted sibling
terms. Those probes use ideal proof membership with real hashes/signatures;
WORK.md owns final acceptance evidence. Nonempty adopted blocks and other fault
classes remain outside the compact implementation, and v3 adoption/live-chain
gates stay open. Final acceptance passed 218 replay groups and 65 real proofs;
the retained report binds 55 source hashes and includes portable/fresh-process
scope cases.

## 2026-09-20 — Permit intrinsic exclusion with complete checkpoint dependencies

**Status:** normative rule and conditional implementation independently reviewed
and verified; delivered together with the source-bound acceptance report.

**Conflict:** C2.10.11's full served-trail requirement keeps a checkpoint unresolved
even where its exact committed proof or issue authorization is demonstrably false.
The [dependency investigation](#2026-09-20--keep-compact-exclusion-behind-an-explicit-dependency-rule)
also found that successful-state reproduction cannot describe a replay that fails
deterministically before its terminal comparison. Authentication of a signed
snapshot preimage and evidence chain is distinct from successful state replay.

**Decision:** pool-v3 §9.1 permits only a non-opening target's local event
trail to be replaced by its existing §9 opening for strict proof rejection or an
exact issue signature under the target backing's K. Require complete directory,
scoped snapshots/header/terms, original record prefix/ranges/order, non-lapse,
valid segment opening, canonical imports/transitive state, last valid prefix,
passed dependencies and record-derived adoption context. The target position must
be outside the required adopted block. No event state, clock reset, import target
or receipt verdict follows from the target. A later valid checkpoint extends the
last valid prefix; neither the faulty prefix nor an older chosen one replaces it.

**Reason and alternatives:** rejection of exact proof inputs under the declared
key or exact issue signature under its committed obligor cannot be repaired by
omitted local state. Retaining all target events is the compatible but more
availability-dependent alternative. Reusing §9 and §12 removes only those bytes;
it does not weaken predecessor or range completeness. New trees, signatures or
asserted dependency edges supply none of that missing state and are unnecessary.
The existing 250-byte framing, exact target fields and 96-byte suffix triples
remain; actual savings depend on the position and unchanged dependency closure.
There is no new primitive, authority, private witness or accepted configuration.
V2 and existing pinned versions remain immutable; this is conditional v3 work.

**Conformance scope and falsifiers:** first support single-backing non-silence
continuations with a valid opening and resolved last valid state, through original
and successor descent. Keep complete selected envelopes. Other scope/silence/
adoption contexts retain ordinary evidence or refuse. Full and compact evidence
must agree on classes and selected state, although independently proven fault
reasons may differ. Remove a predecessor that spent a note: restoration must
refuse, never recover an older unspent state. Wrong target/key/suffix, unsupported
verifier results and resource failures must not create exclusion. Repair must
preserve held-sequence consumption and the exact valid prefix. Scoped lapse and
unknown clocks must retain their priority/refusal. Portable and fresh-process
real-proof checks, then independent integrated review, are delivery requirements.

**Review:** independent source review found no safety blocker. Readback closed
the residual §7.1 full-replay wording and made explicit the supported-verifier
encoding requirement. C0a is satisfied by replacing one availability requirement
with existing bytes while retaining predecessor/range dependencies. Integrated
implementation review independently reproduced an original-path prerequisite
gap: a signed nonempty opening was marked valid before a compact target could be
passed. The original walk now checks opening emptiness before marking that
prerequisite valid. Direct opening rejection, preserved later complete-trail
behavior and compact refusal after the excluded opening were independently
reproduced after the fix. No other material finding remains. The primary's final
focused run passed 153 groups with ideal proof membership, real hashes/Ed25519 and
a synthetic venue; the reviewer independently checked the non-silence fixtures
and its opening substitution.

**Acceptance and cost evidence:** `npm run check` passed 110 files / 1,941 tests
and all packaging, local profile, pilot, store/service/wallet, crash and spent-set
checks. `npm run check:pool:ergo-replay` passed 202 groups / 64 real proofs,
including portable packages and fresh verifier processes. The
[retained report](../docs/pool-v3-local-replay-verification.json) binds 54
LF-normalized source hashes, independently read back against final code. In its
two-event faulty-target sample, a 15,476-byte compact record reduces the complete
package from 50,020 to 34,103 bytes (15,917 bytes, about 32%) with the same classes
and selected state. This is one measured shape, not a general compression bound.
The spent-predecessor sample still refuses when that predecessor is withheld;
same-index repair preserves the held sequence and last valid prefix. Live silence
and shared-scope contexts still refuse without ordinary target history. Real
proof/signature checks use a candidate configuration and synthetic venue/Ergo
headers; no adopted configuration, authenticated live chain, complete-certificate
verdict or production spendability follows. The initial full-check sandbox launch
failed during esbuild startup; the authorized unrestricted rerun passed.

**Spec change:** [pool-v3 §9.1 and C2.10.11/13 at 183c09f](https://github.com/mediumofexchange/money-from-first-principles/commit/183c09f6a796f185fd672350283baca3cc0386a3).

## 2026-09-20 — Keep compact exclusion behind an explicit dependency rule

**Status:** completed dependency investigation. The subsequent
[intrinsic-exclusion decision](#2026-09-20--permit-intrinsic-exclusion-with-complete-checkpoint-dependencies)
defines the narrow normative replacement; the investigation below records its basis.

**Question:** can the existing compact proof/authorization observations replace
a faulting checkpoint's missing event trail in C2.10.11–12 descent? Which other
dependencies would remain, and what would a smaller certificate actually prove?

**Decision:** do not promote observations to exclusion under the current rules.
[C2.10.11–13](https://github.com/mediumofexchange/money-from-first-principles/blob/fb7dd07/pool-fault.md#3-classification)
explicitly retain served evidence, original record prefixes, lapse priority and
the applicable import/descent/clock dependencies. The compact-opening sketch in
pool-fault §7 does not waive those requirements.
[Pool-v3 §9](https://github.com/mediumofexchange/money-from-first-principles/blob/fb7dd07/pool-v3.md#9-fault-evidence-records)
authenticates a target's bytes, while its history and totals remain assertions.
Sections 10.1 and 12.1 retain classification dependencies and forbid substituting
cached verdicts for evidence. A target-history-free exclusion path changes this
availability contract and requires an explicit amendment before dependent code.

**Dependency boundary:** these are evidence obligations, not a new wire format
or an asserted graph accepted from a package. The reader discovers dependencies
from its own request and resolves existing signed/hashed identities.

| Obligation | What it establishes | Current implementation / omission consequence |
|---|---|---|
| Independently selected configuration, kind verifier and scoped signed terms | Meaning of target proof and required keys/messages; no deployment approval | `candidate.mjs`, `fault-evidence.mjs`, `authorization-evidence.mjs`; unsupported verifier or identity supplies no corresponding proof/signature fault |
| Held signed commitment, original witnessed index and complete directory | Checkpoint identity, record position and carriage | `local-replay.mjs` record views and §13 adapter; missing range/directory cannot mean no later carrying checkpoint |
| Snapshot preimage and header/terms for the exact segment | Binds scope, links and the expected evidence digest | `scope-evidence.mjs`; one carried snapshot can bind the shared header, but does not prove sibling state |
| Exact §9 statement/proof/authorization, preceding hash and consecutive suffix | Committed target bytes at the named position | `fault-evidence.mjs`; neither earlier prefix validity nor suffix admission follows |
| Exact named demand statement preimage where needed | Presenter identity for withdrawal/release signatures | `authorization-evidence.mjs`; neither demand admission, standing nor present lock state follows |
| Complete applicable replacement/range evidence at the original prefix | Terms in force and term lapse before validity | `local-replay.mjs`, `scope-replay.mjs`; a later record cannot retroactively change the verdict |
| Original opening and every required carrying clock dependency for silence | Whether the target is already lapsed for any scoped backing | `scope-recovery.mjs`; an unknown earlier reset leaves silence unknown; noncarrying checkpoints do not reset it |
| Target's complete authenticated event evidence | Current prerequisite for deterministic exclusion | `checkpointScope().fullTrail()` and both classifier catches; compact observations do not satisfy it |
| Required imports, last valid prefix and record-derived adopted block | State/admission context and original-event exceptions | `scope-replay.mjs`, `scope-recovery.mjs`, `local-replay.mjs`; omission is not an empty state or an ordinary successor-domain event |
| Selected state's full closure after passing the target | Actual holdings, totals, receipt walk and clocks | `replayLocalPackage` / `replayEvidencePackage`; a target fault supplies no fallback snapshot or restored note |

The table does not require classifying unrelated noncarrying checkpoints or
replaying all global history. C2.10.13 bounds the read by its carrying range and
the dependencies of those checkpoints. Exact shared objects can be reused within
the flat §12 inventory; no new authority or signed certificate is needed.

**Authentication versus failed replay:** the current code is already fail-fast.
`scope-evidence.mjs` authenticates the snapshot preimage and the entire local
evidence chain with `verifyTrailEvidence`. `replayTrail` can then reject a proof
before its terminal history/totals comparison. Both classification catches still
require `fullTrail()` before reporting exclusion. Therefore the accurate existing
claim is *full target evidence authenticated and a deterministic replay failure*,
not successful replay of every event or reproduction of all resulting state.
No state is returned from that failed replay. This is not a demonstrated safety
defect; any complete-certificate amendment must explicitly reconcile the phrases
about reproducing signed digests and replaying every event with this failed-replay
case. It must distinguish digest-preimage authentication, evidence recurrence and
successful semantic state reproduction.

**Counterexamples and acceptance obligations:**

- A valid predecessor spends a note, the next checkpoint contains a bad proof,
  and a successor names an older unspent snapshot. The target's compact fault
  cannot authorize this rollback. Withholding the actual predecessor must still
  refuse; with it present the successor must import exactly that predecessor.
- A shared-scope checkpoint contains a bad proof after one sibling's term ends.
  It is lapsed for the whole scope. Before that end the same missing event
  evidence remains unresolved. A later replacement cannot repair the earlier read.
- With duration 4, a valid checkpoint at index 2, unresolved carrying evidence
  at 5 and the bad target at 7, the unknown checkpoint may or may not reset the
  clock. The target fact cannot choose lapse, exclusion or publication force.
- An adopted recovery event retains original segment/anchor bytes and its original
  admission context. Checking successor context or current standing/deadline can
  falsely reject it. Intrinsic rejection under the correct original proof key or
  required signer is a narrower claim; it must not grow into admission rejection.
- Empty same-index returns inherit the adoption index and still owe the block.
  A compact fault cannot release or reuse held sequences, invent a repair hole, reset a
  clock, decide a receipt or remove that obligation.

**Smallest next capability, conditional on amendment:** define intrinsic exclusion
for supported proof rejection and issue-K rejection, allowing only the faulting
checkpoint's local event trail to be omitted. First settle the exact dependency
rule and the failed-replay wording above with fresh normative review. Retain
complete scope/terms, original record ranges/order, applicable lapse evidence,
ancestor classification and selected-state closure. Do not claim that ancestors
are unnecessary merely because a target's cryptographic failure is state-independent.
Start executable conformance with original, non-silence ancestry through successor
descent and portable/fresh-process reads. Require agreement with full evidence,
target/key substitution refusal, missing-predecessor refusal, later repaired
continuation from the last valid prefix, and unchanged complete selected envelopes.
Unsupported silence/shared-scope/adoption combinations must refuse until their
specific dependencies are implemented and tested. The normative rule must account
for those combinations before any restricted implementation claims conformance.

**Alternatives and C0a:** retaining full trails preserves the current contract and
needs no new mechanism; this remains selected today. Deduplicating exact §12 items
reduces repeated transport without changing classification. Intrinsic certificates
could reduce target-byte availability and verification work, but not predecessor
state or range obligations. Their current opening costs 250 framing/snapshot
bytes plus exact target fields and 96 bytes per later event; no constant-size or
asymptotic saving is established. Trees, another signature or package-supplied
dependency edges add mechanisms without authenticating omitted history. No new
primitive, private witness disclosure, venue authority or runtime format is chosen.

**Evidence and limits:** independent source and exact-proposal review agreed that
a normative amendment is required, identified the failed-replay wording above,
and left no design blocker after held-sequence and independent-fault wording
corrections. Focused execution passed 34 `checkImports` groups in both silence
modes with an ideal proof-membership
oracle, real hashes/Ed25519 and a synthetic complete venue; it exercises compact
proof/issue-signature refusal, full-history controls, missing import/opening
evidence, canonical predecessors and withheld silence dependencies. Final
`check:pool:ergo-replay` passed 194 groups and 63 real proofs, including the shared
scope/adoption cases in `scope-check.mjs`, `recovery-check.mjs` and
`scope-recovery-check.mjs`, plus portable/fresh-process agreement. The refreshed
[report](../docs/pool-v3-local-replay-verification.json) binds 54 checked source
hashes, including the fixture worker's corrected prepared-parameter path.
No smaller exclusion certificate, live range authentication, runtime
capability or product-effort increase is claimed. **Spec change:** none in this slice.

## 2026-09-20 — Resolve compact authorization faults from committed identities

**Status:** implemented, independently reviewed and verified in the conditional
v3 replay experiment. No runtime/configuration adoption.

**Decision:** extend the existing observational §9 boundary to every existing
signature role: issue K, settlement acceptance K, withdrawal presenter and
settlement release presenter. Authenticate the exact target fields through the
held commitment, directory, snapshot and scoped terms before attribution. K comes
from the backing the target names, including an unselected sibling. The presenter
comes from a canonical kind-4 statement whose hash equals the target's named demand
identity and whose domain/backing and key match the supported scope and key rules.
Look up that preimage in the same bounded compact inventory. Its enclosing opening
does not need to authenticate: the target commits the identity, and the hash
preimage fixes the named signer. It establishes no demand admission or standing.

**Why:** pool-v3 §5 excludes proof and authorization from statement identity, §6
fixes the expected signers/messages, and §12.1 resolves dependencies against
existing hashed identities. Requiring full demand history would add availability
dependencies unrelated to a signature mismatch. Supplied key hints would weaken
identity binding. K-only reporting is simpler but unnecessarily omits the two
presenter roles. No wire format, primitive, authority or runtime rule changes.

**Limits and cost:** a `SIGNATURE` fact names the role and expected key; the
operator committed the bad bytes, not necessarily the named signer. Missing,
malformed, wrong-domain/backing or invalid-key demand candidates produce no
presenter fact, while independent K evidence remains. Exact 64/136-byte
authorization fields are supported; zero-owner acceptance messages and malformed
widths remain outside this reporter. Reconstruct settlement messages with the
existing frame helpers independently of proof shape or validity. Proof and
signature failures can coexist; unexpected verifier failures stay visible.
No observation feeds admission, lapse, exclusion, descent, clocks or receipts.
The existing 32-item, 1 MiB, 1024-suffix budgets also bound preimage lookup; signed
message reconstruction adds no signed values or private witness. Signer lookup
is scoped per authenticated mapping, never cached across missing dependencies.

**Review and evidence:** the decisive probe combined real strict signatures,
an exact demand hash preimage and a signed compact target. Independent design
review accepted the identity boundary and identified proof-shape coupling in the
full record helper; message reconstruction now avoids that coupling without
fabricating a proof. Primary and integrated reviewer each passed 103 oracle groups.
The reviewer found no blocker and separately checked real signature/deadline
mutations, maximum-u64 deadline, absent dependencies and malformed messages.
Direct authorization targets cover original-source descent, recovery and sibling
scopes; adopted-block target coverage is indirect through existing original-byte
adoption checks. Final `check:pool:ergo-replay` passed 194 groups and 63 real
proofs, including portable/fresh-process agreement. The retained report binds
54 verified source hashes and six authorization packages (17,928–51,690 bytes).
Runtime/model, circuits, keys and configuration are unchanged; baseline full
check and CI at `7bd70c9` are reused. Documentation/link, syntax and whitespace
checks passed. A wrong signer
passing identity resolution, unauthenticated target attribution or changed
checkpoint verdict would falsify this design. No normative amendment.

## 2026-09-20 — Report compact proof faults independently of checkpoint classification

**Status:** implemented, independently reviewed and verified in the conditional
experiment.

**Decision:** reuse pool-v3 §9 openings and §12 kind-7 inventory items for
observational proof-failure reports in conditional replay. At a held checkpoint,
authenticate the exact directory-backed snapshot and header, every scoped signed
term and their configuration/venue. Authenticate the raw target fields and suffix
before decoding the statement or verifying the proof against the reader's fixed
candidate key. Strict `false` for a recognized proof-bearing checkpoint kind
produces a `PROOF` fact tied to the exact commitment, position and byte hashes.
The report establishes neither authorization, capsule association, admission,
prefix validity nor checkpoint classification. Unsupported/malformed fields and
non-boolean verifier responses produce no fact; verifier failures remain visible.

**Boundary:** C2.10.11–12 still governs descent and clocks. A bad proof with a
missing trail leaves the checkpoint unresolved; complete evidence permits the
existing exclusion path. A lapsed checkpoint remains lapsed with an independently
provable fault. Reports survive later read refusal but never feed classification,
receipt, clock or selected-state logic. Shared scopes can authenticate an opening
against a sibling backing's directory digest. Selected envelopes remain complete;
unvisited checkpoints and no-venue reads supply no compact reports.

**Alternatives and cost:** retaining complete histories is unnecessary for this
narrow proof fact. Treating a compact opening as exclusion would bypass missing
dependencies and could roll back finalized state. A new tree or certificate
signature changes the chosen mechanism without supplying those dependencies.
Reuse costs 250 framing/snapshot bytes, three raw target fields and 96 bytes per
later event. Local limits are 32 compact records, 1 MiB of backing allocations and
1024 suffix entries per record. Proof results are cached per exact evidence item
across scope fallback; each commitment mapping authenticates separately. These
are processing limits, not protocol bounds. No new private data, authority,
normative bytes, proof relation, key or configuration is introduced.

**Review and falsifier:** independent design review accepted this boundary and
required pre-copy budgets, all-scoped configuration checks, verifier exception
isolation, shared-sibling coverage and classification independence. Any compact
item changing a verdict except by resource refusal, or unauthenticated bytes
producing a fault, falsifies the design. Integrated adversarial review found no
remaining blocker and independently passed the import oracle groups and original
segment refusal probe. Input ownership captures one inventory, uses intrinsic
byte views, ignores custom iterators and bounds hidden allocations before copying;
getter changes cannot substitute unbounded payloads after the preflight.

**Evidence:** broad `npm run check` passed, including 110 files / 1941 tests and
operational/crash checks. Final real-proof replay passed 178 groups and 63 proofs,
including portable and fresh-process agreement and the synthetic Ergo adapter.
The [retained report](../docs/pool-v3-local-replay-verification.json) binds 51
checked source hashes. Its compact fault record is 15,476 bytes; the partial
package is 34,103 bytes versus 50,020 for complete replay. These establish
different guarantees: the partial package retains the fault but refuses descent,
while complete replay can establish exclusion. No circuit, key, configuration or
runtime source changed. This applies existing rules; no normative amendment.

## 2026-09-20 — Authenticate import lapse independently of event history

**Status:** implemented, independently reviewed and verified in the conditional
experiment.

**Decision:** apply existing C2.10.4 and C2.10.11–12 by authenticating scope
separately from the committed event chain. A decoded, bounded served-trail
container may supply the header and signed terms even with its records omitted.
The reader binds the directory digest to the exact backing snapshot and its
segment to the header hash, then authenticates every scoped term. Term lapse
reads complete replacement evidence at the checkpoint's own prefix. Silence
lapse additionally requires the original opening and canonical clock dependencies.
Neither case needs the lapsed checkpoint's event history. Selected state still
requires the existing complete selection envelope.

**Rationale:** the full-history requirement refused reads that the public lapse
rule already decides. Reusing header and signed-term bytes in the existing
container avoids another format, signature or trust source. Validation and
deterministic exclusion still require the complete committed trail; a malformed
header plus missing history is unresolved, never permission to roll back.
Scope selection searches for authentic terms rather than allowing an invalid
copy to shadow good evidence. All existing byte/checkpoint/event budgets remain.
This saves fetching and verifying lapsed histories without changing private
data, holder authority, finalized state or original-prefix clocks.

**Review:** the independent design review required exact snapshot backing and
header binding, full evidence on every exclusion path, order-independent term
selection including receipt setup, and historical clock dependencies. It also
identified a prior validity-order issue: an unknown sibling link must not
preempt an authenticated ended term's whole-scope lapse. Those checks and hostile
cases are part of acceptance. A proof-oracle baseline reproduced unresolved
successor reads when the lapsed nonempty history was withheld.
Integrated review independently reproduced malformed-term order independence
using the actual codecs and found no unresolved implementation blocker. The
reader verifies a term signature before strict name decoding, so an opaque
malformed term copy cannot abort discovery of authentic evidence.
Final review identified that directory completeness and sibling-snapshot
agreement are finalization conditions, not prerequisites for authenticating
scope through one carried snapshot. Those checks now follow both term and
silence lapse, with partial-directory lapse cases and a withheld live-history
control. A selectively omitted sibling cannot hide the full header's term end
or erase an already established silence boundary.

**Evidence:** the final focused scope/recovery oracle passed 60 groups. The
real-proof replay acceptance passed 170 groups and 63 proofs, including portable
packages, fresh processes and the synthetic Ergo adapter. The retained report
binds 48 checked source hashes. No circuit, key, configuration or runtime change.

**Spec change:** none. Existing [C2.10.4](https://github.com/mediumofexchange/money-from-first-principles/blob/fb7dd07/pool-authority.md#2-segments-and-complete-commitments)
and [C2.10.11–12](https://github.com/mediumofexchange/money-from-first-principles/blob/fb7dd07/pool-fault.md#3-classification)
already specify this evidence boundary. Runtime adoption, configuration approval
and authenticated live-chain evidence remain separate.

## 2026-09-19 — Count each backing's requests against shared canonical history

**Decision:** reuse C2b.5.2's counter with the scope classifier's latest
canonical checkpoint strictly before the judging index. Count only requests
for the independently selected backing, under its own signed duration,
threshold and window. Non-service clauses need not agree across the scope;
the equal-duration requirement belongs to silence alone (C2b.6.1).

Shared canonical state supplies imported anchors, spent tags and standing
locks. A checkpoint at judgment can advance the selected audit without yet

do not apply recovery effects to that state. Reuse the cached complete

change the grade that each backing declares. Counting against the selected
current checkpoint would clear newly spent or locked tags one index early.
Replaying publication force into the count would similarly clear unadopted
effects before the canonical state carries them. Reusing the existing counter
and strict-prefix classifier avoids a second definition of validity, with
checkpoint, event and publication work charged to the existing budgets.

**Falsification and limits:** compare judgment at a spending/adoption index
and the next index; use different clauses, a missing clause, a dropped backing,
inherited roots and locks, invalid-first/valid-later request proofs, and withheld
sibling ancestry. Design review found no normative conflict. Integrated review

## 2026-09-19 — Read receipts against their complete original scope

**Status:** implemented, independently reviewed and verified in the conditional
experiment.

**Decision:** C2.10.9a–c and C2b.4.3 apply to the receipt's complete immutable
scope. Authenticate every scoped term and the exact held reference, then walk
the original operator's held sequences in order. Reuse whole-checkpoint scope
classification and canonical imports. A transition carrying any original
backing is relevant, including one dropping the independently selected backing.
Every held sequence occupies its place; excluded and noncarrying checkpoints
cannot manufacture a repair hole.

Compute each original backing's silence clock only through the next checkpoint
index, capped at the earliest term end. Stop strictly before the first silence
or term boundary. Inclusion ends the read; later unavailable evidence cannot
erase it. Publication ranges are unnecessary before any gap. Contradictions
already proven survive a later refusal, including fallback from the linear
reader to the scope classifier. Adopted inclusion compares the new local
position/history and original statement, proof and authorization hashes.

one index do not close each other's gap), the gap is open at `i` where

## 2026-09-15 — Candidate Ergo venue profile: full-block exhaustion behind §13 answers

**Status:** candidate profile and offline verifier, implemented in the model
and the Ergo experiment. No specification selects it, no runtime path reads
it, and no real-chain range was read.

**Question:** pool-v3 §13 fixes the record-range answer and leaves to the
venue profile which evidence establishes it and how; C2.3.2 and C2.3.5 name
a venue with its finality rule and lag, and §13.1 adds the attribution and
reassembly rule to that name. The recovery map's A8 and A9 left range
completeness and the kind-4 ordinal open on Ergo, where the v2 adapter reads
an indexed node's word. What does an Ergo profile fix, and can a verifier
establish §13.2's completeness by exhaustion from block evidence?

**Choice:** the [candidate profile](../docs/ERGO_VENUE_PROFILE.md). The
identity is SHA256 over a context, the genesis header id, the depth and one
exact ErgoTree per record kind. The index is the inclusion height, index 0
is below the genesis, `toIndex` is witnessed at `tip − depth` and the lag is
`depth + 1`. An output is attributed by its tree and by `R4` a 32-byte
`Coll[Byte]` subject and `R5` a `Coll[Byte]`; kinds 1–3 are one output at
exact length; a kind-4 object is one transaction's maximal run of adjacent
same-subject outputs at the kind-4 location, its bytes concatenated in
output order, omitted above 131914 bytes. The ordinal is transaction
position then output index in one `u64`. The verifier consumes the reader's
linked header chain and, for every height in the range, the decoded
transaction section; it recomputes each block's root from decoder-derived
ids under the pinned node's rule, scans every output, and answers or returns
nothing: a range not yet witnessed, a height without its section, a range
below an unanchored chain or a foreign venue gives no answer; headers that
are not one linked chain give no verifier; a block of another chain, a
duplicate for an established height or one failing its root is passed over
rather than refusing every read; a transaction the strict decoder refuses is
unsupported evidence for its height. The profile and each request are read
once into owned copies. `model/pool-v3-ergo-profile.ts` implements it
against `model/pool-v3-range.ts`'s frame, whose `copyRequest` now reads each
field once; `experiments/ergo-range/profile-check.mjs` drives it through
Fleet and sigma-rust, with the mainnet genesis header pinned as a fixture.

**Rationale and alternatives:** one location per kind, rather than one tag
register under any script, keeps §13.1's location an address a node can
index and mirrors the v2 adapter's three addresses; the cost is four
identity fields. A uniform `R4` subject and `R5` record for every kind
replaces the v2 commitment's split across `R4`–`R7` with one shape and one
reassembly rule. The run rule needs no piece headers or counts; two
publications of one subject in one transaction must be separated, and a
merged run fails §6 decoding at the publisher's cost. Packing the ordinal as
position then index, rather than a dense count, lets a position be derived
from a transaction's place in the section and its output index alone.
Recomputing the root from decoder ids binds the decoded outputs to the header
through the reader's own decoder without a second parser. Refusing an
undecodable transaction rather than reading past it is what §13.2 requires
of an absence. Header authentication is left to the reader's header source
because proof of work and chain selection are a light client's or a node's
work, not the verifier's; the profile checks linkage, contiguity and the
genesis anchor. Reading the indexed node's box list was refused as the
source because completeness would remain the node's word.

**Findings recorded:** a kind-4 run is one transaction's outputs, so the
kind-4 bound (131914 bytes, the framing over the largest kind-6 record)
exceeds the pinned node's 98304-byte mempool transaction limit, a relay
policy rather than a consensus bound, and under it a record at that bound
would have no location; resolved the same day by measuring the capacity
against the configuration's fixed proof size (next entry). A transaction the reader's
decoder refuses leaves its height without a section, so one node-valid
transaction the decoder cannot read denies every range through its height
until the decoder is repaired: node equivalence of the decoder is a
selection prerequisite, not only its containment. The chain and revocation
reads from index zero are a scan from the genesis on a real chain; P4
measures it, and a start-index rule is a possible spec item.

**Review:** an independent adversarial review found four blockers, all
resolved and read back. One stray, duplicate or root-failing block refused
the whole verifier, letting any supplier of venue evidence deny every read:
such blocks are now passed over and only a height without a section is
unresolved. The profile was not owned, so an accessor could hand one script
to the identity and another to attribution: the profile is copied once on
ingestion. The decoder-refusal denial was not recorded as a limit: it is
now in the profile, this entry and the report. The genesis rule and the
`Coll[Byte]` encoding rested on memory: the mainnet genesis header is pinned
as a fixture and checked, and every fixture register constant is decoded
beside sigma-rust's constant decoder. Adopted optional findings: the request
is copied once before it is judged, which also closed a re-read inside the
range frame's `copyRequest`; only an output's own registers are read;
inaccurate ownership and integration comments were corrected; the mempool
limit is stated as policy; the root rule branches on version above 1 as the
node does; the fixture assertions are described as scan coverage rather
than attribution evidence. The readback verified those fixes and found one
residual blocker: the evidence was still read through the caller's objects,
so a header whose height accessor drifted between two reads registered one
height's root-verified section under another height, a wrong witnessed
index inside a well-formed answer; every header, block, transaction and
output is now read once into an owned copy before it is judged, with a
test whose header height and transaction id drift after their first read.
One residual optional finding, adopted: a structurally malformed block threw
out of the verifier, so a supplier could still deny every read; such a
block is now passed over like a foreign one, while a malformed header stays
a programming failure since the headers are the reader's own chain. A
second readback confirmed the residual fixes. Confirmed by the review: the Merkle rule against
the pinned scrypto tree and the three real roots, single-valued
attribution, deterministic run boundaries, strictly increasing distinct
ordinals, the witnessed index and lag against the v2 adapter, frame order
in every path, and owned outputs.

**Falsifiers and acceptance:** a node-valid transaction carrying an object
at a location that the profile omits; two objects at one height with one
ordinal; a reassembly that depends on anything but output order; a block
whose root the model reproduces from a different transaction set; an answer
for a height the evidence lacks or above the witnessed index; a fixture root
the model fails to reproduce; a real register constant the model and
sigma-rust read differently; a supplied block that denies a read for a
height whose true section is present. Acceptance: the model tests and the
experiment's genesis, synthetic and fixture checks.

**Evidence:** `test/pool-v3-ergo-profile.test.ts`, 9 tests, passed.

## 2026-09-14 — Classify same-segment dependencies from their own trails

**Status:** specified (pool-v3 §7.1 continuity reading) and implemented in
the local replay experiment against a fixture verifier. No venue profile,
imports, silence clock, successor segments or adoption claim.

**Question:** C2.10.11–12 classify every held carrying checkpoint at its own
record prefix and continue a segment from its last valid checkpoint; C2.5
fixes the party in force. The local replay assumed an empty record around the
selected checkpoint, refusing any earlier or later carrying checkpoint and any
admitted replacement. What does "extends the last valid prefix, including its
committed evidence" mean in v3 bytes, how does a reader resolve a dependency
checkpoint's evidence from a package without a first-match lookup, and how is
C2.5 applied to range answers?

**Choice:** pool-v3 §7.1: a later checkpoint extends an earlier valid
checkpoint of its segment exactly where its trail carries at least that
checkpoint's `n` events and §7's history and evidence recurrences over its
first `n` events reproduce that checkpoint's `historyHash_n` and
`evidenceHash_n`; equal length is extension and `n = 0` is extended by every
trail; the comparison is against the last valid checkpoint in the child's own
record prefix, passing excluded and lapsed ones; a shorter or diverging trail
is excluded where it authenticates and unresolved otherwise. The reader
classifies the original operator's carrying checkpoints in held order: a
dependency's snapshot is resolved by its directory digest and its trail by
§10.1 evidence authentication, both by hash, and two authenticating trails
are refused as ambiguous; a deterministic replay failure excludes and is
passed, missing or unauthenticated evidence leaves the read unresolved before
any proof is verified, and the continuity of the committed evidence is checked
before the proof at that position. C2.5 over kind-2 answers is
`replacementChain` in the range model: the lead floor from the verifier's lag
(C2.5.3), the strictly-later rule with the incumbent-naming revocation
(C2.5.4), supersession only before the standing candidate's force and the
lesser identity at one index (C2.5.5), a link past the reading index pending;
it is checked differentially against the runtime walk. The party in force per
index decides which commitments are read (C2.7.1): the selection witnessed at
or after its term's end is `lapsed-selection`; a valid later carrying
checkpoint makes it `superseded-selection` (C2.7.5); a successor's carrying
commitment or a same-operator carrying checkpoint of another segment is
unsupported; an earlier carrying checkpoint of another segment contradicts the
empty opening (C2.7.3). A declared silence clause is unsupported because the
C2b.6.1 clock is not read.

**Rationale and alternatives:** byte-for-byte record comparison would need
the earlier trail beside the later one and duplicate what the chains bind;
both chains already commit every statement, proof and authorization byte at
each position, so equality at `n` reads the same fact from fewer bytes.
The history hash alone would not bind the committed evidence (C2.10.10) and
the evidence hash alone would not name the state receipts bind, so both are
compared. Resolving a dependency's trail by header identity or first match
could pick a substituted terms field or a stale twin silently. Reading a
later valid checkpoint as the snapshot instead of refusing would let the
reader choose the state; the selection is an independent input (§12).
Reusing `successionOf` directly requires the runtime `Backing` and `Venue`
types, whose names differ from v3 terms; a pure walk over admitted entries
reuses the rules and is held to the runtime by test. Cost: one trail replay
per carrying checkpoint, with continuity refusing before the proofs of a
diverging suffix.

**Review:** an independent adversarial review found one blocker: the
revocation rule was applied to every issue statement of a checkpoint at that
checkpoint's index, so a segment continued after K's revocation re-judged a
prefix an earlier valid checkpoint had finalized before it, excluding an
honest checkpoint and rolling a finalized spend back. Fixed: only positions
above the last valid checkpoint's length are witnessed at the child's index
(C2b.1, C2.10.4), with cases for a revocation between two checkpoints and at
the first one's index. Adopted optional findings: a carrying dependency
naming other backings is refused as the selection would be; trails are
decoded once and one that does not decode is no evidence and does not block
the read; the held counters cover the classified term only; the verifier's
lag is in the audit; the second-term check compares the effective index; an
unclassified selection is an explicit programming failure. Recorded, not
changed: two trails that both authenticate one snapshot and differ only in
the terms field are refused as ambiguous, an availability cost a later reader
may resolve; the selection's own deterministic failure keeps the status
`invalid-local-replay` with its check, which is its exclusion class under
C2.10.11. The review confirmed the chain walk as a faithful port of the
runtime walk, the continuity comparison, the own-prefix anchoring, the
hash-bound dependency resolution and the failure mapping.

**Falsifiers and acceptance:** a trail reproducing both hashes at `n` whose
committed evidence differs from the earlier checkpoint's; a valid later
carrying checkpoint the reader passes; an excluded earlier checkpoint that
moves the continuity anchor; a chain reading that differs from the runtime
walk on the same records; a dependency resolved from a substituted trail.
Acceptance: the dependency, exclusion, evidence and chain groups of
`check:pool:local-replay` and the differential chain tests.

## 2026-09-12 — Transfer complete wallets through encrypted offline exports

**Status:** implemented local custody profile; independent adversarial source
review/readback, full check, ideal/real wallet acceptance and 16 interruption
recoveries passed. Current results are in the [wallet evidence](../docs/pool-wallet-verification.json).

**Question:** v2 section 3 requires fresh receiver secrets and stable retry
derivation. How can a wallet move its complete private state without silently
restoring an old request counter or forgetting a reserved input?

**Decision:** support an explicit offline handoff on one trusted device at a
time. A SQLite transaction captures all seven wallet tables, encrypts one
bounded canonical logical snapshot, and persists both the immutable export and
a frozen-source marker before returning. All source mutations subsequently fail
across connections and restarts. Repeating export with the same key returns its
original bytes. Restoration creates a new destination, authenticates the exact
authority and a separately retained SHA-256 export identity, then commits all
state plus import provenance together. A lost import reply is reconciled by
opening that destination and checking provenance, never by blind cloning.

The local envelope uses Node's AES-256-GCM, a random 256-bit recovery key,
random 96-bit nonce, 128-bit authentication tag, and versioned fixed authority
AAD. No password derivation or plaintext staging file is added. The active
database, WAL, swap, dumps and host backups require user-controlled protected
storage; the encrypted export can be kept separately from its secret key.
SQLite temporary sorting stays in memory. Buffer clearing reduces incidental
retention, but JavaScript strings, process memory and host compromise remain
outside the secrecy guarantee.

**Rationale and alternatives:** ordinary online/historical backup would forget
post-backup requests and reservations. A source freeze makes this narrower
offline boundary enforceable without a coordination service. Raw SQLite copying
adds WAL/version handling without solving freshness. Seed-only restoration and
successor capsules are different protocol work and cannot be adopted into v2.
Logical export costs linear time and memory and is capped at 16 MiB of envelope
bytes; unsupported schema or excess size refuses export before source freeze.
This is a controlled transfer, not continuous backup or arbitrary disaster recovery.

**Review obligations and limits:** persist full source authority, validate
legacy contextual rows, guard mutations inside their write transactions and
before network work, and persist the import digest. Stop application workflows
before handoff: local freezing cannot cancel a remote submission already in
flight. Its exact pending command and reservations remain recoverable for
reconciliation. Cipher authentication and an expected digest cannot prove
freshness if the trusted recovery record itself is rolled back. The holder must
retain the latest completed handoff identity independently and allow only one
restored active copy. Restoring twice, replaying an older database with its old
recovery record, or using a pre-freeze legacy executable is outside this profile.
No operator custody, debit/reset key, new finality rule or reservation release is
introduced. Stale exports against a current external identity, conflicting
source writes, interrupted commits and lost replies are falsification cases.

**Implementation evidence:** writable sessions pin full authority and legacy
contextual rows are checked before migration. Explicit SQLite read-only sessions
retain imported-history verification under another same-domain segment. Review
found a destination initialization/import race: the import now checks pristine
state inside its write transaction and retains any intervening acknowledged
request on refusal. Ciphertext is copied before digest/authentication. Fifteen
focused hostile tests, whole-state abrupt export/import checks and fresh-process
real-proof payer/receiver restoration passed; all 1,851 project tests passed.
Pre-custody executables and arbitrary key-holder-created snapshot semantics stay
outside the trusted-producer profile; no trigger layer or general migration
framework is claimed. Device protection itself is a deployment prerequisite.

**Spec change:** none needed; pool-v2 sections 3 and 9 and all protocol bytes,
circuits, derivation and runtime pins stay unchanged. See the Node
[GCM API](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptocreatedecipherivalgorithm-key-iv-options)
for explicit tag-length enforcement.

output positions than three), not only when needed; no assumed fee-flow
frequency or phone budget is hidden in the choice.

Each extra output adds a 32-byte public commitment, 89-byte capsule, one leaf,
one restore trial and output constraints on every spend. There is no extra
input ownership/path proof. The price is persistent capacity and scan work,
including zero padding. It is not justified by pretending padding adds real
anonymity. The shape does not add input positions, cross-scope atomicity,
reliance settlement or a universal fee coin. Issue, burn and lit settle do not
gain fee outputs; their service funding cannot shave issuance/redemption or
become a prerequisite for the public recovery rules.

**Privacy and service obligations:** a sequencer paid a fee is also a payee.
It sees its fee backing/quantity/opening and the associated statement. In a
same-backing fee flow it consequently knows the payment backing; a fee quote
proportional to payment value would also disclose that value. The first
direct-fee flow uses a fixed quote independent of payment size. A separately
chosen fee backing avoids that necessary same-backing inference but still
narrows candidates to the scope, may identify them in a tiny scope, and links
the fee to the statement. Sponsored service remains available. Construction's
visibility table and product privacy claim must state the payee exception.
Neither payment input leaves nor other output openings are exposed by the fee.

C2b.5.1–2 has no fee quotation, submitted transfer or payment predicate: a
holder can decline all quotes and still file valid counted holding requests.
An unpaid price does not clear a count, excuse silence or change a venue
remedy. This is a real service-pricing/free-request grief limitation, not
something a private fee schedule silently fixes. Ordinary fee ownership
preserves supply verification and gives the operator no custody/debit power.

**Review and evidence:** the independent reviewer required all extra-output
checks, backing conservation even for zero outputs, explicit fee-recipient
inference and preservation of unpaid non-service requests. The reviewer also
corrected a draft that forbade spending a pending fee: ordinary local roots
already permit pending descendants, which share the tail's failure risk.
The exact draft now preserves that rule and idempotency under price changes.
The reviewer supports four at the measured cost and read back the final
probe with no unresolved material finding: 17 positive host checks, 35
rejection cases and five real proofs, all 14,656 bytes. Every extra output
has isolated foreign-backing, zero-owner/rho, commitment and u64-overflow
cases; all duplicate pairs and cross-backing value shifts fail. Field-ABI
bypasses over unchanged ACIR prove the added-output and digest limb range
checks survive hostile witness encoding. The selected four-output ordinary
fee flow and its widened-sum boundary both prove.
[Recorded evidence](../docs/pool-fees-verification.json) identifies the final
retained sources and measurements; `npm run check:pool:fees` reproduces them.
The probes demonstrate cryptographic feasibility, not v3 runtime admission,
quote transport, wallet durability, full finality, device budgets or venue
publication acceptance.

## 2026-09-09 — Receiver-prepared outputs restore from bound public capsules

**Question:** F3 asked whether restoration changes the note or its relation.
Construction C1.2 and pool-v2 §3 have the payer create rho and privately
supply the opening; C4 leaves a lost opening lost. A seed cannot reconstruct
payer-chosen private data. Adding X25519 alone would encrypt the opening but
would not tell a sender how to derive a fresh `owner = H(secret)` that only
the receiver can spend, or tell a restored wallet which per-address keys to
try without a persisted address range.

**Decision:** Select exact receiver-prepared output requests for the smallest
supported profile. The receiver already contributes a fresh owner for every
expected payment. It now chooses the complete requested backing/value note,
derives secret/rho from its seed and a durable fresh request identifier, and
encrypts that identifier/backing/value to itself. The payer inserts the exact
opening and opaque capsule. This adds no recipient key agreement and leaves
the note, owner and nullifier formulas unchanged. Issue/spend/burn relations
add one aggregate delivery digest as two constrained public limbs; the public
trail carries a fixed-size capsule for every output position. This is a v3
configuration change, not a compatible extension to v2.

The exact contract is `pool-delivery.md`, C4.1–8. Profile 1 uses HKDF-SHA256,
HMAC-SHA256 rejection sampling and AES-256-GCM through platform cryptography.
A separated recovery key derives a different AES key for each domain and
commitment; the nonce and AAD are fixed for that key. The only encryptable
plaintext is the internally derived request producing that commitment, so
same-key retry has identical plaintext and AAD. An arbitrary-commitment
cipher API would violate the construction. Recovery reveals neither spend
keys nor a public stable scanning key. New randomly selected request IDs
are persisted before exposure, exact requests are immutable, and a restored
wallet chooses fresh IDs instead of assuming a lost address counter.

**Alternatives and cost.** Omitting restoration leaves accepted notes dependent
on local openings or their original payer. A static scan/address key permits
payers to link recipients; per-address X25519 still needs a seed-recoverable
locator and delivers payer-chosen data after the request. A changed algebraic
owner could support noninteractive reusable addresses but adds ownership and
circuit work the selected request flow does not need. A receipt-only capsule
commitment would fail to bind an unsigned spend's data to its proof. Putting
encryption inside the circuit would prove a property the receiver can check
against its own exact request, at much higher cost. The selected design
replaces the payer's private-opening delivery and avoids these extra mechanisms.
It gives up reusable addresses for arbitrary unsolicited amounts: a changed
backing/amount needs a new receiver request. It does not add another round to
the existing per-payment owner exchange.

Capsules are 89 bytes. The delivery digest adds two field encodings, 64 bytes,
per issue/spend/burn statement, before record framing: 242 extra bytes for two
outputs or 331 for three. Zero/change positions carry the same capsule shape.
Restore costs one trial HKDF/AES-GCM per capsule-bearing output, plus note hashing for matches
and all existing public-proof, ancestry, tree and spent-set replay work.
The backer's lit settlement needs no capsule: its secret derives from a
separate seed key, public demand identity and acceptance deadline; C3.5
already publishes rho. A restored backer must still verify that a settlement
actually created that output, including force/adoption where relevant. Every
public settlement scanned costs a secret/owner derivation before matching.

**Invariants, trust and limits.** Only the receiver knows its spend secret;
per-backing conservation and public supply verification remain unchanged.
A payer cannot alter a received capsule without changing the proof-bound
delivery digest, but a payer can construct useless ciphertext initially.
The receiver accepts only its exact requested output and capsule with
verified finality, or explicitly pending receipt liability. Missing full
trail/authority/record evidence is unresolved, not zero holdings or fallback
to an older balance. Independent replicas must retain the complete package;
content addressing provides no permanent availability guarantee. Restoration
is scoped to named domains/venues/backings and a verified current boundary;
the seed does not prove coverage of unknown venues. Local invoice metadata,
unpublished requests, pending receipt backups and rollback coordination remain
wallet work. Seed compromise has no forward secrecy or protocol reset.

**Review and falsifiers:** independent review of the actual contract required
an explicit created-output predicate for lit settlement: a matching owner,
commitment and absent nullifier cannot make an expired/unadmitted release a
holding. C4.7 now requires canonical inclusion or venue force and distinguishes
an output awaiting adoption from an ordinary anchored spendable note. The
review also checked conditional Construction amendments, one-use requests,
key/AAD separation and fixed-length ordered vectors. Feasibility must fail if
wrong seed/context/output/capsule produces a holding, changed delivery inputs
verify under the original proof, or a fresh process needs the payer's secrets,
original wallet journal or original operator. Candidate measurements and
reproducible tests are recorded in the deployment probes; they do not establish
v3 finality, network completeness or a finished wallet.

The retained `npm run check:pool:delivery` probes pass 22 host checks and a
real modified spend proof. A fresh process reconstructs unspent notes from
its seed and prevalidated synthetic public data without the old journal;
force-created notes awaiting adoption remain separate. Node and WebCrypto
produce identical capsule bytes. Review also required explicit in-circuit
range evidence: changing only the delivery ABI metadata to `Field` leaves
the ACIR unchanged, yet `2^128` fails in each limb after a passing control.
Both changed public limbs reject the original proof. Cost is +16 gates
(19,034 to 19,050), unchanged subgroup and 14,656-byte proof. Host boundaries
reject forged byte-array lengths and ignore overridden iterators. The final
promoted sources and matching reports were independently read back with no
unresolved material finding. [Recorded evidence](../docs/pool-delivery-verification.json)
includes source identities, measurements and explicit limitations.

**Spec change:** [`02d911c`](https://github.com/mediumofexchange/money-from-first-principles/commit/02d911c)
on `spec/pool-delivery-restoration`: new `pool-delivery.md` C4.1–8 and conditional
Construction C1.2/C4 amendments. No v2 source, bytes, circuits or keys change.

## 2026-09-09 — The v3 recovery choices: the notice is the proof's public inputs, only settlement or withdrawal discharges a demand, and the release publishes no non-membership proof

**Question:** The [v3 recovery map](../docs/POOL_V3_RECOVERY_MAP.md) laid out
what `moe/pool/v3` must carry to instantiate the presentation, recovery and
fault contracts, and its independent review left ten choices whose contract
sentences were owed before any byte is fixed. Eight sat in
`pool-recovery.md`: whether a demand's notice is hashed separately or is the
proof's public inputs (C3.2–C3.3); whether the holding proof forbids one note
in two positions (C3.2); whether the settlement's `rho_out` is public (C3.5);
whether a withdrawal is a bare signature over a demand identity or a signed
statement (C3.6); whether the release publishes non-membership proofs
(C3.6, C2b.3.2–3); whether a demand past its deadline is discharged from the
standing-demand record (C3.7, which read "A demand past its deadline is
discharged from the standing-demand record" against Construction §C3's "the
claims are committed against payment until withdrawal or settlement");
whether a spent tag voids its demand whatever index the spend was admitted at
(C3.8); and how an acceptance, which names no backing, is routed (C2b.3.2).
One sat in `pool-fault.md`: the evidence chain's hash and contexts, written
as `H` and `T_EVIDENCE` for a construction to fix (C2.10.10). One sat in the
count: a request is unsigned, so anyone can republish it, and C2b.5.2 did not
say at which index a copy is read.

**Decision:** Decide all ten in the contracts, before `pool-v3.md`, because each
is version-independent —
they say what a construction must do, not what its bytes are. The notice is
the proof's public inputs and the demand's identity is its `statementHash`,
so one object has one identity and the circuit carries no second hash. The
relation requires the positions' nullifiers to be distinct and the door
requires distinct nonzero tags: one note in two positions doubles the
quantity a demand claims and leaves it unsettleable. `rho_out` is public, so
the backer rebuilds its note's opening from the record with no delivery from
the party the settlement is a remedy against; every other field of that
opening is public already. The withdrawal is a `withdraw` statement the
presenter signs by `statementHash`, binding the segment as a demand's proof
binds it, so a withdrawal an operator held back cannot be applied under a
segment the holder never named. The release publishes no non-membership
proof: every reader that decides force replays the snapshot for its forest
and standing demands, so it holds the spent set and checks absence itself,
and a published proof restates what its reader already has. Only a
settlement or a withdrawal discharges a demand. A spent tag voids its demand
from the index the spend was witnessed at. An acceptance is read beside the
demand it names. The evidence chain is `SHA256` over frames under two
prefix-free contexts, binding the position. A request is read at the first
index its identity was witnessed at.

The two that were more than tidying: C3.7's deadline discharge was a latent
exclusion bug. A settlement admitted at a horizon inside the deadline can be
witnessed by a checkpoint long after it, and a replayer that pruned the
record at the index it read would refuse that settlement and classify an
honest checkpoint as excluded (C2.10.11). Construction §C3 already said the
claims stand until withdrawal or settlement, so the contract contradicted the
core. The deadline still ends the lock and still gates the door and the
venue, and a demand past it is unsettleable because no settlement of it
passes the door (C3.4, C3.8) — not because a reader removed it. And C3.6's
non-membership proofs were a mechanism with no consumer; removing them takes
two proofs out of every release, about 1.2 KB where the spent set holds 10⁵
nullifiers.

**Review:** an independent adversarial reviewer returned three blockers and
nine material findings on the first commit; two blockers were defects in its
own new sentences. Construction still said the holder proves non-membership
and that §C2b.3 needs it, and Construction outranks the contract, so §C1.2,
§C2b.3 and invariant 23 now say what must be established rather than what is
published. C3.8's void, as first written, voided every *settled* demand,
since a settlement spends its own demand's tags, and it was retroactive,
which contradicted the latch Extensions reads: a holder that spent an
unanswered note to a fresh one, as §C1.5 tells it to, would have erased the
dishonour it had already suffered. The void now excludes the demand's own
settlement and runs from the index the spend was witnessed at. Third, a
request had no defined identity to be read at a first index by, and the
refresh the count depends on did not exist — re-proving under a later
accepted root is impossible while an operator stalls and admits nothing,
which is exactly when the grade must count. C2b.5.1 now frames the request as
a statement of its own kind over its own public inputs, with a holder-chosen
refresh value the proof binds: only a party that can prove the note mints
another identity for one tag, a stranger's copy still extends no window, and
the count still deduplicates by tag. The material findings are resolved in
the same commit: a tag carries one lock per standing demand and a discharge
releases only its own, which the C3.7 change made reachable; the
authorization field is named per kind so `signatureHash` has one meaning;
the demand's relation constrains the presenter limbs, the instant and the
deadline, so no declared public input is left unconstrained and rebindable;
C2.10.11's classes cover an authorization that is neither a proof nor **K**'s
signature; a settlement is refused by its own segment binding rather than its
demand's; and the retention price is stated as the backing's life.

A second, bounded review read those fixes back, since the refresh value was a
new mechanism written under review pressure. It returned two blockers and
eight material findings, none reopening a decision. The refresh value was
said to be "constrained as a field element", which is no constraint at all,
and under a proof system that drops an unread public input from its
verification equation one witnessed request would have carried every refresh
value — restoring the copy the first-index rule exists to stop. It is now
range-checked, under a rule C3.2 states outright: a relation of this contract
constrains every public input it declares that no signature binds, so a proof
binds it whatever the proof system. That rule exposed a padding position's
anchor as an unread input, now `0`, with the door and the venue reading the
anchors of positions whose tag is nonzero; a settlement keeps a spend's free
anchor because its release signs the whole statement. The second blocker was
worse: the settlement refusal written for the first review would have excluded
every honest return from silence, because an adopted release carries the
segment binding it was judged under (C2b.4.2) and a history that omits its
adopted block is excluded (C2.10.11). It now excepts the block. Also fixed:
the index a spend voids from is the earliest canonical checkpoint holding it,
so two readers do not compute different payouts over the latch's interval;
C2.10.11 names every key a kind's authorization is verified under, a
settlement's carrying two; C2.10.8 asks a new proof only of a kind that
carries one; the refresh value is derived, not drawn (invariant 26); and
Construction's amended invariant 23 and §C1.2 no longer rest on an argument
the same amendment refuted — a replaying reader can check absence against a
bare root too — but on the reader that does not replay, saying plainly that
no rule in force today spends the capability and why it is kept.

**What is not decided.** `pool-v3.md` waits (map item A12). The configuration
hash covers all six circuits and the arity bounds and *is* the domain of
every note and nullifier, so freezing v3 before the delivery/restoration (F3)
and fee-shape (F4) decisions would charge every backing a second successor
migration across a changed domain; an extensible configuration that could
absorb them later is the mutable verifier authority the whole-project design
review refused as F1. F3 is next, since restoration may reach the note itself
and so should precede an arity measurement. A22 is new: with no proof
published, the 256-high sparse accumulator's only reader is a replayer that
rebuilds it, at about 430 node hashes per insert — measured, and not the
reference's to remove, since a bare SHA-256 of the frame costs 2.96 µs here
against `node:crypto`'s 2.38 µs. Replacing it is a v3 layout choice under the
amended invariant 23 and §C1.2, provided absence remains establishable and
the root remains a function of the set alone, recomputable per statement.

At decision time the executable model was not yet aligned: it did not check
the demand's nullifier distinctness, modeled the withdrawal's authorization
as public-field equality, read acceptances without their demand, counted a
republished request at its own index, and used one evidence context without
the position.
The follow-up implements first-publication request counting and binds the
explicit 64-bit refresh in the ideal relation and statement digest. The other
departures remain; the runtime stays pinned to v2. Seed derivation and crash
persistence of the refresh counter are wallet work, not model evidence.

Request-model review found that retaining only the first publication's proof
would let an invalid first copy shadow a later valid proof of the same
statement. Counting now preserves the first identity index while accepting
any matching valid proof witnessed strictly before the judging index. Proofs
at that index or later cannot validate an earlier read. Malformed model
encodings are ignored as invalid requests; unexpected programming failures
remain visible. Regressions cover both proof arrival orders, strict index
boundaries, aged-out copies, same-anchor renewal, refresh bounds and binding,
tag deduplication, routing and malformed publications.

**Follow-up review, 2026-09-09.** A fresh independent review of the net
contract changes found one remaining ambiguity in C3.7's settlement
predicate. Demand D1 expires at 100 but stays standing; D2 locks the same
note until 200; at checkpoint 150 a withheld, previously authorized
settlement S1 of D1 must not consume D2's lock. The existing general lock
rule and the model's `applyEvent` already forbid it, but the explicit
settlement checklist omitted that condition. The reviewed correction makes
the other-demand lock exclusion explicit rather than pruning D1 or changing
replay's deadline rule. It adds no object, trust assumption, privacy leak or
storage; the existing lock lookup supplies it. Independent readback approved
the actual diff. A model regression checks the live-lock boundary at 200,
expiry at 201, and expired-D1 settlement with no other lock; existing adoption
tests retain the publication's original judging index.

The same review corrected map omissions for demand padding's zero anchor
and the request's 64-bit, deterministically derived refresh value, and the
stale A22 claim above. Construction's older signed-presentment/reputation
wording still conflicts with the pool's unsigned holding proof and fresh
presenter key. That predates this slice and must be reconciled before v3 is
frozen or demand admission reaches the runtime; this correction does not
claim to resolve it. It is now resolved by the
[presentment attribution decision](#2026-09-09--pool-demands-authorize-notes-without-identifying-the-demander).

**Spec change:** [`a166161`](https://github.com/mediumofexchange/money-from-first-principles/commit/a166161)
on `spec/recovery-lock-clarification` makes the C3.7 lock predicate explicit.
The earlier [`7a510f1`](https://github.com/mediumofexchange/money-from-first-principles/commit/7a510f1)

## 2026-09-08 — Adoption retains witnessed proof evidence

**Question:** C2b.4.2 adopts publications whose force was judged once, while

coverage are described in [fault recovery](../docs/POOL_FAULT_RECOVERY.md).

## 2026-09-08 — Intervening silence retires a pool segment and lapses its unfinished receipts

**Question:** C2b.6.1 lets an unrelated commitment close a backing's clock,

open gap. A disjoint Y opening could therefore restore X's old continuation

**Decision (2026-09-08):** Generalize the existing new-segment return: the first open gap strictly after
a segment's witnessed opening is its silence boundary. Later resets cannot
restore it. Keep the separate current-index gap guard for a continuation at
the opening's own index. Earlier finality is unchanged; a fresh opening adopts
all publications with force through its own index before serving.

Use that same proven boundary for receipt lapse, ending the existing receipt
walk at the earlier of silence and term end. Earlier inclusion, contradiction
and abandonment survive. An unfinished receipt otherwise lapses even without
a carrying return; `after` implies no signing time. A supplied repair at or

conservative; discard and receipt lapse require an actual witnessed boundary.

published recovery acts; authenticated complete interval and clock evidence.
The model enumerates finite record intervals, not every bigint index. This
does not supply production range proofs or solve availability. Moving the
adoption boundary would need additional ordering and proof rules; checking
only releases would omit effective demands and withdrawals. No new signed
bytes or transfer authority are added. Fault exclusion, its clock alternatives
and R6/R7 remain separate unselected research policies.

Independent adversarial review found a delayed-adoption bypass after a second
gap. Adoption now refuses that retired segment too, while exact receipt retry
and historical replay remain available. Permanent tests cover the unsafe
departure, both fault-clock choices, actual versus predicted gaps, receipt
precedence, evidence refusal, sparse indices and same-index opening behavior.

## 2026-09-07 — The pool's presentation and recovery contract: whole-note demands by tag, a lit settlement to the backer, force once at the venue, and the return as a new segment

**Question:** pool-v2 §7.4 left presentation (§C3), the non-service object
(§C2b.5), snapshot redemption's venue leg and the adoption of what the venue
witnessed (§C2b.3–4) outside the construction, to be specified together. The
2026-09-07 finality decision fixed the policy (finalized holdings, no
redirection) but not the objects: what a demand names in a pool where a
spend has no payee or signature, how a lock reserves a hidden note, what the
settlement is, how a release at a dark operator's venue is judged, and how a
returning operator adopts it without an operator-asserted read index.

**Decision:** `pool-recovery.md` (spec `820cd51`) defines C3.1–8, C2b.5.1–2,
C2b.6.1, C2b.3.1–3 and C2b.4.1–2 for a later construction version. The
choices, each revisitable at its number, and the alternatives refused:

- A demand names whole notes by `tag = H(T_TAG, nf)`, at most `inputs` of
  them; partial or larger presentation is wallet consolidation first. A
  settlement with change was refused for one relation and one reading of
  invariant 27.
- The acceptance's `owner` and the settlement's quantity and output are
  public, so the operator and any stranger can check that a settlement pays
  the backer. Redemption was already lit at the backer (§C1.4).
- The pending-lock set and standing demands are recomputed from the
  history's `demand`, `withdraw` and `settle` statements (invariant 23), and
  a lock reserves without consuming. No attempt timeout in the single-operator
  core; cross-operator presentation stays the Extensions profile.
- The non-service request is the holding proof without a segment binding, so
  a handover inherits it, as §C2b.5 requires.
- A publication has force once, at the first index at which it has any,
  judged against the record strictly before it. Republication of identical
  bytes (derived randomness makes a re-release identical) is judged again;
  a duplicate cannot confer force twice.
- The return is always a new segment; a continuation witnessed in an open
  gap lapses for its whole scope, on a public condition descent passes as it
  passes a term end. The adopted block is every publication with force up to
  and including the opening's index, at positions 1…k. The alternative, an
  in-segment adopted block, needs an operator-asserted read index.
- The adoption index: a settlement not yet adopted by any checkpoint still
  counts against the next gap's holdings, so a note settles once across
  silences.
- A carrying checkpoint the reader finds invalid blocks recovery and the
  count as it blocks descent (C2.10.3); it is not a licence to read an older
  state. What remedy a backing has against a provably faulting operator,
  beyond the fault proof and **E**'s replacement rule whose successor faces
  the same blocked descent, is open (neither contract defines it).

Independent adversarial review of the first revision (`820cd51`) returned
twelve findings; the second revision (`3676757`) adopts them all:

- A publication is read for the backing its statement names as a public
  input, never for the venue's label, or a stranger relabelling a release
  under a sibling backing could brick the return (high).
- A lock stands only until its demand's deadline; a punctual operator
  refusing one holder could otherwise freeze the note forever while the
  count read it as served, against §C3's unilateral withdrawal (high).
- Invalid live carrying evidence blocks the count as it blocks the snapshot,
  stated rather than left to two readers (high; remedy recorded as open).
- The instant is a checkable window `w − 2·lag ≤ instant ≤ w − lag`; the
  presenter key is fresh per demand; an acceptance is evidence only where
  its deadline exceeds its witnessed index by more than the lag.
- One no-commitment duration per scope, so a sibling's clause cannot lapse a
  backing that promised none; a commitment carrying nothing for a backing
  closes its interval and adopts nothing, and the next carrying segment's
  block reaches back to its adoption index.
- An adopted statement is judged once, at its own index; imported lock
  events apply in ancestry order and unrelated prefixes sharing a tag are a
  conflict; the count reads strictly before `t`; the request's tag and
  anchor are costed.

The choices were accepted on 2026-09-08 subject to checking their relative
merits. The recorded assessment is: whole-note
demands keep one relation and read invariant 27 literally, costing a
self-spend for change; the lit settlement lets any stranger check that the
backer was paid, where a hidden output would move that dispute off-protocol;
the demand's own deadline bounding its lock is §C3's "the window is the
holder's" with no second clock; the segment-free request is forced by
§C2b.5's handover rule; one duration per scope is the only coherent option
once a checkpoint finalizes a whole scope or nothing (C2.10.3); the
always-new-segment return is the only variant that makes the adopted block a
function of the public record alone; the instant window and force-once rules
are the checkable forms of Construction's own bounds; and the adoption index
is what keeps a note from settling once per silence. The invalid-live-
evidence stance is not this contract's choice but the authority contract's
(C2.10.3), and the remedy it leaves open stays open. On that assessment the
choices are confirmed.

**Cost:** three statement kinds, one relation family and one hash tag in the
next configuration; a public tag per demanded note; five publication kinds
at the venue; a replayer that reads the venue record from a checkpoint's
adoption index to the next opening; re-proof and resynchronization after
every return. Reliance sets, claims-paying payouts, cross-operator
presentation, the venue bridge and cross-construction adoption stay excluded.

## 2026-09-07 — Shielded recovery preserves finalized holdings without payee redirection

**Question:** Construction C2b.3 redirected snapshot redemption to "the payee
that spend names" during a challenge window. A private spend has two opaque
outputs, can merge inputs, and proves secret knowledge rather than naming a

## 2026-09-07 — A carrying scope change decides a receipt: proven repair lapses it, an elective change abandons it

**Question:** C2.10.9a selected "the first held checkpoint belonging to a
different segment" and required the sequence immediately before it to be
absent. An operator can hold checkpoints of an unrelated segment, carrying
none of the receipt's scope, between the receipt's segment and its repair, or
before a continuation of the segment that includes the receipt. Read
literally, such a checkpoint both excused the receipt at a boundary that
changed no scoped backing's state and filled the hole that proves repair.
C2.10.9 forbade using a new segment to excuse a live receipt without naming
what a reader calls a receipt whose segment lost a scoped backing's carrying
state electively, and no rule named the verdict at the present index.

**Decision:** Make two clarifications, with no new mechanism or signed object.
The original record flagged these for confirmation under the authorization
to merge reviewed work; that historical qualification is retained here:

- The C2.10.9a boundary is the first held checkpoint of another segment that
  carries a backing of the receipt's scope. Checkpoints carrying none of the
  scope are passed over: each occupies its sequence and is neither a hole nor
  a transition; the hole is any sequence the record never held between the
  segment's last held checkpoint (at least `after`) and that boundary.
- C2.10.9b: where that carrying transition is canonical, witnessed while every
  original term is live, and not a repair boundary, the receipt is abandoned:
  neither final nor excused, and unfinalizable, since no later checkpoint of
  its segment extends that backing's state (C2.10.4). At one index the verdict
  is final, then contradicted, then abandoned, then lapsed (moved past, repair,
  scope boundary), then pending. A position occupied otherwise at or below
  `after` contradicts whatever became of `after`; omission above a moved-past
  `after` is that lapse.

`readPoolReceiptStatus` implements the verdict, relating and replaying the
record in ascending order and ending at the first inclusion, so that a later
checkpoint the reader cannot relate or validate erases neither a proven
inclusion nor a proven contradiction; `readPoolReceiptRepair` follows the carriage
reading; the model's `classify` and its `lapseWithoutCarriage` departure show
that lapsing at a non-carrying checkpoint misreads a receipt the record
finalizes.

**Alternatives and costs:** Reading a non-carrying checkpoint as a boundary
excuses an operator on a record that changed nothing for the scope and
reports a finalizable receipt as lapsed. Leaving the elective case unnamed
reports a dead, unexcused receipt as pending forever. Requiring the transition
to be the operator's immediately preceding sequence falsely accuses an
operator that lawfully repaired after a failure while another segment's
checkpoint landed in between. Where every later checkpoint of the operator
carries a scope backing, every C2.10.9a verdict is unchanged; an operator
that leaves a scope for an unrelated one, carrying none of it, no longer
lapses its receipts at that opening but leaves them pending until a term
ends or the segment continues. The cost is a reader that must obtain the
directory of every held commitment of the operator since `after`, and the
history of each checkpoint of the receipt's segment up to the first inclusion.

**Spec change:** [C2.10.9a–b](https://github.com/mediumofexchange/money-from-first-principles/commit/da80f856186f438a0df24f7e071923720264c72e).

## 2026-09-07 — Proven failed-publication repair can lapse unfinalized receipts

**Question:** C2.4.3 permits repair when a signed commitment fails publication,
and C2.10.9 permits stale-state discard, but C2b.4 explicitly lapsed only
receipts whose own `after` was moved past. PoolStore reproduced held sequence
1, an unfinalized receipt after 1, failed sequence 2 and empty repair 3.
The receipt's reference and original terms remained live.

**Decision (2026-09-07):** Permit lapse at proven repair.
C2.10.9a generalizes existing failed-publication lapse: the first held
different-segment checkpoint must be a canonical empty opening, immediately
preceded by an absent sequence greater than `after`, with all original terms
live. Complete canonical interval evidence must preserve inclusion and
historical contradiction independently. A conflicting occupied position at
`after` also contradicts the receipt; absence there does not. Only neither
inclusion nor contradiction permits lapse at the boundary. Later final
inclusion remains independently meaningful. Missing/invalid evidence fails
the proof, not the payment.

This preserves existing repair and adds no signed object, circuit, unfinalized
import or trust authority. It permits deliberate abandonment of an
unfinalized payment by withholding a checkpoint: the record cannot distinguish
that from publication failure. Requiring continuity instead would need a new
cross-segment mechanism, contrary to the current finalized-only import rule.
The bounded `readPoolReceiptRepair` API implements this one boundary; it does
not claim a complete global classifier or authorize service/discard.

**Spec change:** [C2.10.9a and C2b.4](https://github.com/mediumofexchange/money-from-first-principles/commit/bdd359971185463bf5e734eadaa0ced639774ca1).

## 2026-09-06 — pool-v2 instantiates the authority contract: a domain-only configuration, a public scope tree, the segment in every statement, one anchor per input, and finalized import

**Question:** The authority contract (C1.2.1–2, C2.10.1–9) required a new
construction whose "layouts, circuits, keys and remaining supported objects"
were unpinned, and the reference held only the fixed-operator `moe/pool/v1`
runtime and an ideal-cryptography model. The specification left open how the
domain excludes the operator, how a proof establishes private scope
membership, how a statement is bound to one segment, how an import is
handed to a verifier, and whether v1's code stays.

**Decision:**

- **`pool-v2.md` is the core construction's layout**, `moe/pool/v2`. The
  configuration frames only the six circuit identities, the helper and four
  bounds (32, 16, 2, 2); its hash is the construction domain and every
  implementation of the pinned sources derives the same one. A note commits
  to the domain in place of v1's pool identity. **E** names the original
  operator beside the construction (evidence clause `0x05`), as the genesis
  link of the replacement chain.
- **The scope is a depth-16 Merkle tree over `H`** of sorted
  `(backing, link)` entries with its own leaf and node tags (1005, 1006);
  every spend input, padding included, proves membership under its link
  in-circuit, and outputs are covered by naming an input's backing. Depth 16
  costs about a third more hashing than v1's spend; a larger scope is another
  version.
- **Every statement's public inputs begin with the domain, the segment
  identity as limbs and the scope root** (9, 11 and 13 fields). The segment
  limbs are bound as public inputs and read by no constraint; `check:pool`
  proves every public input binds. A statement is therefore a statement for
  one segment, and re-proving after a lapse keeps nullifiers and outputs.
- **The segment header** frames domain, venue, operator, the opening
  commitment sequence and each entry's link and exact opening — an empty
  book as sequence 0 with zero operator and root, otherwise the commitment's
  operator, sequence and directory root — and its hash is the segment
  identity in the genesis history hash, the snapshot and the receipt. A
  same-operator opening must be below the segment's sequence (C2.10.5).
- **A spend names one anchor per input**; the forest is `z_32`, the local
  roots and every root certified by the imported prefixes.
- **Import is one finalized prefix per distinct opening commitment**,
  checked against itself (local events match its length, its directory
  matches its events) and against the header (operator and directory root,
  scoping the backing), then merged: events deduplicate by (segment,
  position) with identical effects, a nullifier or output in two distinct
  events is refused, totals fold over the closure within bounds, the spent
  set is rebuilt from the closure. `Segment.replay` walks supplied
  checkpoint evidence — commitment verified, directory root matched, the
  checkpointed segment replayed to its length with its own openings, its
  directory compared entry for entry — once per checkpoint, refusing cycles
  and missing ancestors. Whether an opening is canonical, a checkpoint final
  or a term ended is the record's (C2.7, C2.10.3–4): the pool sequencer,
  next.
- **Receipts sign the domain, segment identity and scope root** beside the
  v1 fields and are verified against a `SegmentAuthority` derived once
  from the header, so a receipt of one segment attests nothing under another.
- **The v1 runtime is replaced in place**, not kept beside v2: one
  production path, one mechanism per property. Its bytes, pins and
  verification record stay in `pool-v1.md` and git history; it never carried
  claims, so nothing crosses.

**Alternatives and costs:** keeping v1 code beside v2 doubled every parser,
circuit and check for a construction the specification calls historical.
Binding the scope root alone, without the segment identity, would let a
proof serve two segments of one scope; binding the segment alone would leave
the root unspoken in the frame the receipt signs. A scope over backing names
without links would let one root stand for two terms. Two review lanes over
the circuits and the frames, admission and import ran before merge; their
findings and dispositions are in `WORK.md`'s evidence.

**Spec change:** companion branch `spec/pool-v2` in
`money-from-first-principles`: `pool-v2.md` and the pins in its §15;
Construction C1.3, `pool-authority.md` and `pool-v1.md` point at it.

## 2026-09-06 — Private service scopes import only finalized shared history

**Question:** Construction C1.3 bound the immutable configuration to its
operator while C2.5–8 promised independent operator replacement. Hidden
mixed-backing statements also lacked an authority and history boundary.
The exact conflict and host evidence are in
[the diagnostic](https://github.com/mediumofexchange/reference-ts/blob/f3ca8b4/docs/POOL_SEQUENCING_BOUNDARY.md).

**Decision (2026-09-06):** Preserve private spends and independent backing replacement. The construction domain fixes
cryptography, relations and bounds, excluding operator and segment. Each
backing retains its own witnessed replacement chain. Notes and nullifiers do
not change across operator terms, scope changes or different membership paths.

A public scope names the currently served backing/term pairs for one
operator, domain and venue. The proof privately checks scope membership for
every input/output, including padding. A segment fixes that scope and its
per-backing canonical opening checkpoints. A checkpoint finalizes the whole
scope or none; a term ending lapses the entire incompatible unwitnessed tail.
Elective scope changes must first finish live receipts and the latest signed
commitment. Restart preserves the signed journal and tail. Active local
journal ownership ends when another segment or resumed instance replaces it.
Final inclusion and historical contradiction evidence survive later lapse.

New segments import only finalized canonical predecessors and their supplied
ancestry, with locally decreasing witnessed-index/sequence ranks. Shared
events deduplicate by segment and position; distinct-event nullifier or output
conflicts reject. Certified source roots remain a forest beside the new local
tree. One combined spent set covers all imported and local events. Missing
history blocks replay. Invalid live carrying evidence cannot silently become
an earlier state; only authenticated absence or actual whole-scope term lapse
licenses descent. Same-index predecessor reads exclude self and later records.

**Alternatives and costs:** Whole-pool replacement would remove independent
operator choice; fixed-operator-only service leaves existing claims without
a replacement remedy. Neither is the chosen product. Raw shared-history
unions permit abandoned-note resurrection and replay. A private
backing-to-anchor relation is unnecessary under exact finalized imports:
every imported b event already belongs to b's canonical ancestry, and serving
b imports its complete spentness. The counterexample returns if either full
scope finality or canonical import is removed.

The chosen cost is public scopes, source-anchor provenance, shared tail
finality and permanent transitive data availability dependencies. Replacement
is independent in authority, not in historic data availability. A scope uses
one venue; no global venue or replacement coordinator is introduced. A
cross-venue bridge and atomic cross-operator objects remain separate work.
This requires new frames, circuits and keys; existing v1 bytes cannot be
reinterpreted. The new model uses ideal proofs/signatures and local journal
ownership, not a real circuit, durable implementation or full scheduler.

**Spec change:** Companion branch `spec/pool-authority`, normative commits
[`f842335`](https://github.com/mediumofexchange/money-from-first-principles/commit/f842335)
through [`a219aad`](https://github.com/mediumofexchange/money-from-first-principles/commit/a219aad),
defines C1.2.1–2 and C2.10.1–9 in `pool-authority.md`, integrates Construction,
and corrects v1's unsupported replacement claims. Implementation model branch:
`feat/pool-authority-model`.

## 2026-09-05 — The claim layer: E declares the construction as clause 0x05, the host hash is a pinned Poseidon2, and admission verifies the proof before one synchronous view

**Question:** pool-v1 fixes the pool's frames, hashes and admission rules but
leaves three things to the implementation: how a backing's **E** carries the
construction and configuration inside canonical encoding v1; how the host
computes the in-circuit hash without a proof backend; and how an asynchronous
proof verifier fits admission "against one committed view" (§6) when two
statements are in flight.

**Decision:**

- **E's declaration is evidence clause `0x05`:** `u32 length ‖ construction ‖
  32-byte configuration hash`, sorted among the other clauses; no clause means
  the transparent profile; a construction string other than `moe/pool/v1` is
  refused by the decoder as an unknown clause is, since terms a reader cannot
  check are worse than none. The `setting` field becomes a union
  (`transparent` | `pool`) derived from the clause. The transparent ledger
  refuses a pool backing. No new evidence tag: the clause list (decision
  2026-08-20, slice 12) already carries independent blocks.
- **The host hash is a pure-TypeScript Poseidon2** with Barretenberg's
  constants, bound to the circuits by the permutation's published test vector
  and hash outputs recorded from bb.js 5.2.0, and re-compared with the backend
  in `check:pool`. The alternative, hashing through the WASM backend, would
  make every wallet and verifier computation asynchronous and make the proof
  backend a hard dependency of the package. `@aztec/bb.js` is an optional
  peer dependency reached only through `pool/barretenberg.ts`.
- **Admission verifies the proof first, against the statement's bytes alone,
  then runs every state check and the transition with no await between
  them.** The proof is the one asynchronous step and reads nothing in the

- **The receipt's content is recorded, not yet signed:** `AcceptedStatement`

review findings. Deliver one constant-payout root, signed
wallet operations, a transactional operator and explicitly trusted local witness.
Reuse the reference ledger doors; journal canonical commands and exact responses
before exposing them. Serialize all writers through one SQLite database and
replay deterministically on restart. Registration and witness advancement are
administrative; wallet transport authority cannot issue or move claims.
Reject empty initial witnessing, incompatible identities and unbounded growth.
The 10,000-command limit makes replay's current cost explicit. External witness
publication, rollback protection and checkpointing remain later work; process
durability must not be advertised as recovery against a hostile operator.

Execute the previously selected root framing change before persistence fixes
the old format in place: a complete sorted directory of names and snapshot

Fix canonical backing identity at signing/verification/registration and serialize

review, built tarball installation and real process termination in acceptance

Payment verification binds caller-pinned terms, recipient and amount; a receiver
must separately deduplicate fulfillment. The pilot's application API can report

## 2026-09-04 — Slice 39 verification: a venue answers an exact sequence; pending receipts remain non-final

**Question:** The independent verification artifacts under
`scratch/panel39/verify2/` reached a case the fix round had recorded as
residue: two increasing commitments of one key can be witnessed at one index.
The venue kept both, but `eraIndex` could ask only for the latest commitment at
an index, so it called the lower sequence `"died"`. That turned a genuinely
witnessed era into the excuse reserved for a commitment the venue never took.
The same verification also showed that a malicious signer can jump its signed
sequence and create many real holes with one witnessed commitment, cheaper
than the earlier entry claimed.

**Decision:** A venue must answer the witnessed index of an exact commitment
sequence. `ErgoVenue` orders same-index commitments by sequence before applying
the existing strictly-extending filter, and both venue implementations expose
`witnessedAtSequence`. `eraIndex` uses that exact read for older eras. Thus
every commitment the venue kept remains final and nameable even when a higher
one shares its index; only a sequence the record truly skipped is `"died"`.

Real holes remain lapsed. This is unavoidable from the public record: a
dropped in-flight commitment and one the signer withheld have the same absent
bytes. A large signed sequence jump can create many holes cheaply, but it
cannot erase any witnessed commitment after the exact read, and receipts in
those absent eras were pending rather than final. A payee must not treat them
as payment before the named commitment is witnessed. A holes-per-commitment
grade may price that behavior more visibly later; it is a policy improvement,
not a correctness condition for this slice. The in-flight expiry is governed
by the venue lag and therefore applies even when the backing declares no
longer silence-and-recovery duration.

**Evidence:** The current-head rerun of `v1-control.mjs` resolves sequences
0–3 to their exact witnessed indices. `v2-cheap-park.mjs` still demonstrates
the honest indistinguishability above while its same-block case now resolves
all sequences 0–6 as held. Focused venue, era, fault, and blind-window tests
pass, including direct assertions that both node orders retain the lower
same-index sequence. Removing either the deterministic ordering or exact read
breaks that test.

**Spec change:** `construction.md` on `spec/the-blind-window` now requires the
exact sequence answer and distinguishes in-flight expiry from the optional
longer silence clause.

## 2026-09-04 — Panel: the blind window — an operator serves the book its own signature put the record on, and a receipt names the commitment rather than the index

**Status: the design panel for slice 39, and the design the slice builds.**
Three review angles (security/adversarial, the replaced-mechanism inventory,
practicality/spec/simplicity), each with prototype builds of every candidate
run against the suite and each other's probes, over the residue slice 38's
review filed as F11 and its round handed forward. Reports and probes under
`scratch/panel39/`.

**The finding, measured.** On a venue that reads behind its chain — every
venue this repository ships for production — `commit` rewrites the seat's
pin to the new commitment and `serves` compares that pin against the
record, which will not show it for the venue's lag. So an operator goes
dark after every commit:

| depth (Ergo, ~2 min blocks) | dark per commit | fastest cadence | payments refused |
|---|---|---|---|
| 1 | ~4 min | ~6 min | 50% |
| 3 | ~8 min | ~10 min | 70% |
| 6 | ~14 min | ~16 min | 81% |

Every readable grade says the operator is healthy throughout — `isSilent`
false, `isOverdue` false, `gapOpen` undefined — and the refusal a payer
gets is an instruction addressed to the operator, telling a stranger to
call `takeOver`. `awaitingTakeover`, which CLAUDE.md's boot rule makes the
restart checklist, re-arms after every commit, so a monitor written to that
rule cannot tell an unfinished boot from an ordinary commitment.

**What the angles found, each probe-proven:**

- **A dropped transaction bricks the operator permanently** (practicality's
  F5): the pin never matches, `serves` is false forever, `commit` refuses
  the silent drop forever, and the only exit is a hand `takeOver` — whose
  signal is identical to a superseded twin's, the one condition the
  unbounded pin exists to make detectable. §C2's "one detectable condition
  rather than three silent ones" now covers four, one of them benign and
  common on a real chain.
- **The force rule is inverted for the lag** (inventory's F4, security's
  F6): the process that published goes dark and the superseded twin keeps
  co-signing, where the force rule says "the one writer that keeps writing
  is the one whose pin keeps up".
- **A restart inside its own window equivocates against itself** (inventory's
  F1, security's F2), following CLAUDE.md's boot rule exactly: `takeOver`
  refuses the operator's own in-flight state and accepts only the stale one,
  and the next commitment then carries a sequence the record has already
  seen — `isEquivocation` true at every depth, with no attacker. Latent only
  because `ErgoVenue` refuses to publish.
- **The record-derived sequence collides after a dropped transaction**
  (security's F3): `ErgoVenue.nextSequenceFor` answers from the finalised
  height, so the operator re-signs a sequence it already signed over a
  different root. `LocalVenue` refuses the second; a chain does not, and
  `ErgoVenue` admits both boxes.
- **The floor's one safe clock does not exist** (all three): at the floor
  lead the incumbent has zero clocks to land a commitment inside its own
  term, at every depth measured — the one-per-index guard takes it when the
  previous commitment lands at the record's index, the blind window takes it
  otherwise.
- **The one-per-witnessed-index guard is unpinned by the whole estate**
  (inventory's F6): deleted, 944 of 944 still pass, and its message appears
  in no test. Its stated hazard is unreachable on a lagging venue anyway —
  one index is one block, so nobody can read the first commitment before
  signing the second — while the hazard the lag does deliver is the
  equivocation above.
- **And the coupling that decides the slice** (all three, independently):
  `serves` and `era()` are one read of the record wearing two hats, and the
  blind window's door refusal is what keeps receipts checkable today. Open
  the door and leave the era alone and an act co-signed in the window reads
  `contradicted` — a stranger-checkable lie about an honest operator's own
  log — whenever the in-flight commitment turns out to be its last, which is
  exactly the return from silence, the handover, the crash and the seizure,
  the cases where a receipt is the only evidence there is. Predicting the
  index instead (`signingClock + lag`) turns one slow block into a receipt
  that reads `unrelated` for ever, because §C2's own sentence says
  inclusion is "bounded below by the lag and above by nothing".

**Decision and review synthesis.** Two of three angles
recommended it and the third recommended its safe half; the split was over
whether to open the door at all, and the measured cost of leaving it shut is
the table above.

1. **An operator serves the book its own signature put the record on.** The
   seat keeps, beside its pin, the record identity that pin stands **on**;
   `serves` is the pin against the record's last, **or** the pin against
   this operator's own published-and-unread commitment while the record has
   not moved off what it stood on. The twin is detected at exactly the index
   it was before — the twin's publication moves the record off `over` — and
   the publisher is no longer the side that goes dark.
2. **One commitment in flight.** No second commitment until the record shows
   the first or the venue's lag has passed since it was signed. The expiry
   is what makes a dropped transaction a stale seat one `takeOver` from
   repair, instead of a brick; the one-in-flight bound is what keeps the
   era a reader must resolve at most one commitment ahead of the record.
3. **The era a receipt names is the commitment, not the index.** `after`
   becomes one more than the sequence of the last commitment the operator
   had **signed**, so zero still means none; a reader resolves it against
   the record and answers `pending` while it has not landed. The domain tag
   goes to `moe/receipt/v3`: the field's width is unchanged and its meaning
   is not, which is the collision a tag exists to prevent.
4. **The one-per-witnessed-index guard becomes one arm of the in-flight
   rule, not a layer beside it.** Its purpose is dissolved at any lag above
   zero — the era is no longer an index, and with one commitment in flight a
   second is signed only after the first is in the record, so two can never
   land at one index. At lag zero nothing is ever in flight, so the rule's
   other arm is that guard exactly: the record must show the last commitment
   at an index before this one would land. [As built: the slice's own tests
   caught the in-flight arm alone letting two commitments land at one index
   at lag zero, so the guard is kept as that second arm rather than deleted —
   which also answers the panel's inventory angle, which had filed it as
   unpinned by the estate: it is pinned now, by a test and by a mutant.]
5. **The sequence is the operator's own count**, never below the record's:
   `max(record + 1, highest signed + 1)`.
6. **A process commits nothing until the venue's lag has passed since it
   registered.** At lag zero this is no wait at all. It is what makes the
   restart safe: whatever the process published before it died is either
   readable or gone before it signs anything.
7. **The floor rises to `2·lag + 1`.** Slice 38 sized the floor for a
   sequencer that could commit at every clock; this slice makes one every
   lag, so the rule-holder can put the whole safe range inside the operator's
   in-flight window. The security angle's F7 said one extra index sufficed;
   its sweep tried three alignments and the worst is later than the three.
   At lag zero `2·lag+1` is `lag+1`, so no `LocalVenue` fixture moves.
   [Corrected by the review's spec angle, and re-measured: the cadence this
   slice delivers is one commitment every **lag**, not lag+1 — it is an
   index FASTER than main, because the retired guard cost one — and the
   least lead with a safe clock at every alignment is therefore exactly
   **`2·lag`**, at lags 2, 3, 4 and 7 alike. `2·lag+1` ships anyway: one
   index of slack, and it is what keeps lag zero the single index it has
   always been without a `max`. The sweep this entry first cited fixed the
   record's index and varied the incumbent's cadence, which is the wrong
   axis — the rule-holder picks the index — and the sweep the panel cited
   cannot run against this build at all. The one that settles it is the
   review's `scratch/panel39/review/spec/build/sp2-floor-alignment.mjs`.]

**What it costs, taken deliberately:**

- **The receipt encoding changes** and the era readers with it. That is the
  expensive half and it is not optional: shipping the serving half without
  it is the one combination all three angles priced as worse than doing
  nothing.
- **Resolving an era costs a verifier a binary search** over reads the
  contract already has — no new `Venue` method, and not on the operator's
  door path, which knows its own era's index and skips the question while a
  commitment is in flight.
- **A restart is commit-dark for the lag**, and a brand-new operator waits
  the lag before its first commitment. It may co-sign throughout, once it
  has taken over.
- **A handover's minimum lead doubles**, from `lag+1` to `2·lag+1` — on Ergo
  at depth 3, from ten minutes to eighteen. It widens the revocation window
  by the same amount, which is the one thing slice 38's fix panel found
  bounding supersession would have cost.
- **`lag()` reaches the co-signing path** for the first time, through the
  expiry. A venue that over-declares it holds a stale book serving longer;
  the contract already requires the id to bind it.
- **Two honest processes of one key still equivocate**, whatever the
  sequencer remembers, and no candidate closed it. That is the one-writer
  party rule, and what this slice stops is *manufacturing* it for a party
  that obeyed the rule.

**Residues, recorded:** a restart after a *dropped* commitment whose bytes
somebody kept can still re-sign that sequence, because this repository has
no persistence layer for the operator's own count — a party rule until it
does, and clock-derived sequences are the recorded alternative; an expired
in-flight commitment is a sub-duration return from silence that no era
reader names (its window receipts read `pending`, the excusing direction);
a delayed rather than dropped transaction that lands after its expiry is
unmodelled, and `LocalVenue`'s own sequence refusal is a courtesy the
`Venue` contract does not require; the payee still has no reader for "who
is in force where the act lands", and now none for "is this operator inside
its own window"; `serves` gains a venue read on the hottest path in the
file and nobody has measured it.

**Spec change:** §C2 and §C2b, on `spec/the-blind-window`.

## 2026-09-03 — Panel: the lead time — the floor is the venue's lag plus one, and a door reads force where an act signed now is first witnessed

**Status: the design panel for slice 38, and the design the slice builds —
superseded in part by the entry above: the door (point 2) was removed after
the review found it a lever and a fix panel found nothing that closes the
lever short of removing it or bounding supersession; the floor (points 1 and
3) stands.** Three review angles (the replaced-mechanism inventory,
security/adversarial, spec-simplicity-practicality), each with prototype
builds of every candidate
run against the suite and each other's probes, over the erasure slice 36's
regression round filed as F4 and the next slice was 38: a
replacement effective at the index it is witnessed puts the incumbent's
commitment at that index in no term. Reports and probes under
`scratch/panel38/`; the brief's design space was A (effective strictly later
than witnessing), B (a lead of one witness interval), C (attribute the
boundary commitment to the predecessor's term), D (a party rule).

**The finding, re-measured — and it is not the boundary, it is the depth.**
All three angles found the same thing from different sides. `ErgoVenue`
reads at the indexed height less its depth and dates a record by its
inclusion height, so an act a party signs at clock *c* is witnessed at
*c + depth + 1* or later, and a record witnessed at *w* is readable only from
clock *w*. The incumbent's usable notice under a lead *L* is therefore
*L − depth − 1*: under A it is *−depth* on every real chain, zero at best. The
security angle's table (`s3-depth-erasure.mjs`): an incumbent obeying §C2 to
the letter — "until the effective index the predecessor governs and goes on
serving" — makes its last commitment at a clock strictly before the effective
index and has it witnessed AT that index, erased, under leads of 1, 5, 20 and
100 alike. At depth 0 the attack is reactive (publish after seeing the
commitment, the same block); at any depth it is pre-armed, aimed at the
incumbent's next scheduled commitment, whose cadence E declares. **No
candidate in the brief reads the depth, so none closes the class.**

**What the angles found, each probe-proven:**

- **A closes nothing on a lagging venue** (the inventory's `i4b-in-flight`,
  byte-identical to main), **vacates the void rule's only killer test**
  (mutation-proven: the floor refuses the fixture before the void rule is
  reached), retires the zero-lead configuration two tests were named for,
  moves past readings for every short-lead record (`i9`), and narrows the
  revocation exemption's stated width from the wrong file.
- **B is a lock whose key length the burglar chooses** (security's F3): the
  rule-holder is the backer by default and the backer writes E, so an
  interval of 1 — or no witnessing clause, which is legal — is A again. With
  an honest interval a pre-armed record still lands the erasure (B requires
  exactly one commitment period of lead, which is the next scheduled
  commitment: the record is aimed, not delayed); a stolen operator key stays
  in force for a declared interval (a day of Ergo blocks at 43,200); the fee
  dial and the rotation dial become one number; the walk reads a field of E
  for a venue it does not identify; 69 tests move.
- **C convicts an honest retiring shared operator** (security's F7, the spec
  angle's F3): its next batch commitment drops the handed-over backing —
  its own door refuses to carry it — and, placed in its term, that drop is a
  permanent stranger-checkable rewritten history, in both argument orders,
  for doing what §C2 says to do. Not exceptable: the reader cannot see what
  a commitment carries.
- **C2 (the tie to the successor) reopens the erasure** (F8): the attacker's
  successor syncs an index early and commits at the boundary, and its
  commitment becomes the book.
- **C′ (inclusive for the book only, `lastCommitmentInForce`) closes the
  boundary index alone** — the window past it stays *depth* wide — and, found
  in synthesis: it makes the predecessor's out-of-force boundary commitment
  the book while placing it in no term, so a truncation published there is
  inherited by the heir and provable against nobody. One lever traded for
  another, and the party holding the new one is the same party.
- **D is B with the code removed**, and unfollowable under A or C: the
  incumbent sees the record after the last block that was safe.
- **No candidate makes two honest readers disagree** (security's F12, an
  incremental against a cold reader over every index): each rule is a pure
  function of the backing's fields and the record's own witnessing.

**The three recommendations, and why none was taken as filed.** The
inventory recommended C with three riders (the spec's "fixed object"
sentence, the heir's re-sync at the boundary, and `settledInPart`'s gate) —
but C's conviction of an honest operator is not a rider. Security recommended
C′ with a party rule about the depth — the truncation lever above, and it
leaves the depth window open. The spec angle recommended B′ (B with a
one-index floor) — the burglar's key. What all three had established, without
naming it as the rule, is that the hole's width is the venue's lag and the
cure is notice measured in it.

**Decision and review synthesis, implemented in slice 38.**

1. **A replacement's lead is floored at the venue's lag plus one.** The lag
   is the least number of indices by which an act signed at the venue's clock
   is witnessed after it: zero where publication lands at the clock's own
   index (`LocalVenue`), the depth plus one where a chain includes in its next
   block and the venue reads behind it by the depth (`ErgoVenue`). It is a
   constant of the venue's finality rule — inside `ergoVenueId` already — so
   naming the venue agrees it, and it goes on the `Venue` interface as
   `lag()`. `admitted` refuses `effective < witnessed + lag + 1`, the
   generalisation of the anti-backdating filter that stood there: judged once
   per record, clock-free, against the venue that answered it (slice 37's
   memo is untouched). **The property, stated: the record precedes, on every
   party's clock, every act it can void.** An act witnessed at or past the
   effective index was signed no later than that index less the lag, which
   the floor puts strictly after the record's witnessing — so a commitment
   the predecessor signed before it could read the record is inside its
   term, and one it signs after is its own choice. On a venue with no lag
   this IS candidate A; A's failure was measuring "strictly later" in a unit
   the venue does not use.
2. **A door reads force where an act signed now is first witnessed, as well
   as at the clock.** `Sequencer.retiring`: in force at the clock and a
   handover taking force within the lag — the pen where the act lands is the
   successor's, so the co-signature could only be witnessed in no term, the
   erasure reached by the incumbent's own hand. The incumbent's doors close
   the lag before the effective index and name the successor; the successor's
   open at the index itself, once nothing the predecessor could still land in
   its term is unread (opened the lag early, the heir co-signs on a book the
   predecessor's last commitment can still move — the same race, from the
   other side). Only `inForce`, the co-signing door, asks it: `serves`,
   `awaitingTakeover` and what a commitment carries do not, so a retiring
   operator's commitment still carries the book — harmless once witnessed out
   of force, because it is not the book — and nothing reads as a stale seat.
   Zero-width on a venue with no lag, where the clock and the landing index
   are one and every test written before this slice is unchanged. Without it
   the floor is theatre: the reference implementation would hold the notice
   the floor buys and co-sign into the void anyway.
3. **The boundary stays where it was.** Force and the book pass together at
   the effective index; a predecessor's commitment witnessed at or past it is
   neither the book nor placed. Every re-attribution the panel built moved
   one of the two and opened a hole in the other.

**What it costs, taken deliberately:**

- **The zero-lead configuration is gone**, and the 35d decision "zero lead
  hands over late, never locked out" is reopened knowingly: a record below
  the floor is no record, the incumbent goes on serving, nothing is stalled
  or locked out, and the honest path is the same record dated the floor
  ahead. The claim those two tests made — late, never locked out — is made
  at the floor now, and their names say so.
- **A lagging venue prices a handover at a stall of the lag** (the
  incumbent's doors shut, the successor's not yet open). The acts refused
  there are exactly the acts that could only have died; "every TIME rule is
  a refusal and never a balance", and "claims go illiquid while the operator
  is dark — do not accept one" is the same shape.
- **A revocation carries the floor** — its index is inert, but a self-naming
  record dated below the floor is no record — and **at the floor on a venue
  with no lag the revocation window is empty**: widening it is the
  rule-holder's, by declaring more lead. Both now in §C2.
- **The `Venue` interface grows by one method.** Yesterday's decision
  deferred `replacementCountFor` for a constant factor; this one carries a
  security property that lives nowhere else, and a third-party adapter that
  declares less than it lags reopens the erasure — stated in the contract.
- **Past readings move for a record with a short lead** on the two code
  versions: the 35d migration note, widened from an unbuildable record class
  to a buildable one. Nothing is deployed, which is why now.
- **Twenty-three fixtures move by one index; three tests the floor vacated
  are re-shaped** (the void rule's killer, now pre-armed at a seated heir's
  link; two term tests that passed with nobody seated) and the conscription
  test's record is dated past the floor (the signature check runs before the
  floor, so it was never vacated — a re-date, not a re-shape); one cache-key
  test re-aimed at the possession door, since force cannot arrive at an
  unmoved clock any more; two renamed; nine added, with a `LaggingView` test
  double carrying `ErgoVenue`'s two read properties over a `LocalVenue`.
- **Inclusion is bounded below by the lag and above by nothing.** The floor
  gives the incumbent a chance, not a guarantee: what it still holds
  uncommitted when it reads the record is what a slow block costs it. The
  party rule: commit the moment you read a handover naming you; and the
  payee's: read a pending handover before you treat a payment as final.

**Residues recorded, not fixed:** `serves` reads stale for the lag after
every commit on a lagging venue (the commit pins its own commitment; the
record shows it only once finalised) — security's F11, a liveness hole for
any operator on `ErgoVenue`, its own slice; the payee-side reader ("who is in
force where the payment can first be witnessed") is `operatorAt` at the clock

**Spec change:** `spec/the-lead-floor` on the paper repo, five sentences of

## 2026-09-03 — Four recommendations, decided: the lead time now, the platform verifier and the root framing next, the count method and the drifting clock deferred

**Status: the recorded decisions on the five items slice 37's handoff
flagged, recorded for the instance that takes over.** Point 1 (the same-block
erasure) is slice 38, in progress on `slice/38-the-lead-time`. The other four
are decided as below and not built.

1. **The same-block erasure in §C2 — taken, as slice 38.** A replacement
   effective at the index it is witnessed puts the incumbent's commitment at
   that index in no term, so a witnessed final payment vanishes and re-spends,
   unprovably, for one record from the rule-holder — the backer by default,
   the party that owes the money. The panel decides the closing rule
   (strictly later than witnessing, or a minimum lead of E's witness
   interval, or a boundary re-attribution) and its cost; the reasoning that
   it must close: security over convenience, and the convenience lost — a
   handover taking force in its own block — is nothing a party needs.

2. **The platform's Ed25519 verifier where it exists, the library as the
   fallback — recommended, next, gated on one proof.** Measured on this
   machine: the library's strict verify 4.35 ms, Node's own 0.19 ms, a 23×
   gap, and every cost figure this project has produced is that number (the
   cold resume's floor, the walk's exhibit price, the door's residual). The
   rule against other crypto dependencies is about dependencies; the
   platform's verifier is not one. The gate: verification here is strict and
   non-ZIP215 and the platform follows RFC 8032, so the two must be shown to
   agree on the non-canonical and small-order vectors the invariant-02 tests
   hold, in both directions, before the switch lands — two verifiers for one
   property is the shape the panel rule exists for. The switch lives in the
   one funnel every verification already passes through
   (`verifySignatureStrict`), with the library kept for platforms without
   Ed25519 in their crypto (browsers vary). Panel first.

3. **Frame each snapshot's name beside its digest in the commitment root —
   recommended, before any real venue write-side or persistence work.** An
   exhibit proving a commitment carries nothing for a backing is today every
   other backing's whole log (19.2 MB at 100 backings × 1,000 entries, 21
   hours on a 2 kbit/s link — the slice-36 practicality angle), which prices
   the walk-back off a LoRa-class link and makes "keep every committed state"
   expensive. With `stateRoot` writing `key32(name); key32(digest)` per
   snapshot, the same proof is the sorted (name, digest) list, 64 B per
   backing: 6.5 kB. The root stays 32 B; nothing on the wire grows. The cost
   is that every existing commitment becomes invalid — zero now (nothing
   deployed, the npm package unpublished) and growing with every real
   commitment minted later. It changes invariant 23's root, so the spec is
   corrected first and gets a panel; the window to do it cheaply closes when
   a format becomes load-bearing anywhere.

4. **The `replacementCountFor` Venue method — deferred.** It removes a
   threefold residual on a flooded door call (~44 ms against ~14 ms at 4,000
   junk records, the sequencer's cache key decoding every record five times
   per call) by adding a method to the narrowest interface in the system,

## 2026-09-02 — Panel: the cold walk — a record is judged once, against the venue that answered it, and junk leaves nothing behind

**Status: the design panel for slice 37, and the design the slice builds.**
Three review angles (security, simplicity/consolidation/cost, the
replaced-mechanism inventory), each with prototype builds run against the
suite and each other's, over the finding slice 36's regression round handed
forward as F3: `publishReplacement` refuses only bytes that do not decode, so
anyone files replacement records for any backing for free, and the succession
walk verifies two strict Ed25519 signatures per record before it looks at a
single link, on every uncached walk. Reports and probes under
`scratch/panel37/`.

**The finding, re-measured — and the brief's own probe found wrong.** The
security angle found that the probe the finding was filed on
(`s2-venue-junk.mjs`) never checked that its cold resume succeeded: the first
call threw, so its "warm" and "door" columns timed a `TypeError` on
`undefined`. The corrected numbers, on this machine, where one strict verify
is 4–6 ms (`@noble/curves` on this CPU — the whole of the cost):

| junk records | cold resume | live chain, per block | a holder's one grade |
|---|---|---|---|
| 0 | 51 ms | 17 ms | 0.3 ms |
| 4,000 | 56 s | **14.5 s** | 13.5 s |

The live-chain column is the one nobody had: the sequencer's walk cache is
keyed on the witnessed index, which moves every block, so every block
re-verified every record for every backing with a replacement rule — a
liveness attack, not a slow boot. And the "warm" path was never flat: the
cache KEY is `replacementsFor(name).length`, and the local venue decodes every
record to answer a length. Every verifier-side reader (`fault.ts`,
`recovery.ts`, `receipt.ts`, `ErgoVenue.sync`'s own frontier loop) paid the
full cost per call.

**What the angles found, each probe-proven:**

- **Verification is one step and everything after it is byte compares**,
  two and a half orders of magnitude apart (a verify ~5 ms; the whole walk
  over 4,000 already-verified records ~54 ms). The verdict is a pure function
  of (backing name, rule key, record bytes) and never changes.
- **Verifying only candidates (D1) buys exactly zero verifies** — the
  attacker sets `predecessor = backing.name`, so every record is a candidate
  at the genesis link — **and breaks the walk three ways** if the verify
  moves past the fields-hash dedup, the same-index tie or the self-naming
  exemption: a junk twin of the honest record (same fields, garbage
  signatures) published first takes the dedup slot and then fails, so the
  signed handover disappears; a lesser-hash junk record at the honest one's
  index skips it; an unsigned record revokes a co-signed handover. The suite
  is green under all three. The order rule that falls out: **verification
  stays strictly before the fields-hash dedup**, because the dedup's key is
  deliberately not the record's identity.
- **A verdict memo keyed on the fields hash is poisonable** (the brief's
  fact 2, run): the twin published first caches `false` under the shared
  hash, and two venues holding the same two records in opposite orders — the
  ordinary case, since §C2 publishes a replacement at both venues — disagree
  permanently about who is operator. The full record bytes are the only sound
  identity for a verdict.
- **A memo keyed on the backing name alone is poisonable by a hand-built
  `Backing`**: the brand is a phantom type with no runtime property, so an
  object carrying the real name and a substituted rule key is a Backing at
  runtime, and under a name-only key its admitted records are served to the
  real backing (both angles, independently). The key must carry the rule key.
- **Re-keying the sequencer's cache on the record count alone (D4) fails an
  existing test** ("a rotation beyond the pending horizon is seen when its
  index arrives, with no new record published") and would not work anyway:
  the count is the adversary's to move, one junk record per block restores
  the attack, and a count can be held still while the records change. D4's
  underlying split IS sound — 16,400 (record set, index) pairs over 400
  adversarial sets show `successionAhead` at any index is a prefix cut of one
  clock-free walk — but it aims at the wrong step and its key is the hazard.
- **A memo that holds only ADMITTED records, positionally, leaves nothing
  behind for junk**: heap delta across a 4,000-record flood is zero, where a
  per-record verdict map retains ~1.5 kB per junk record forever and costs
  13 µs per record per walk to rebuild its keys. Per-walk residual after it:
  the venue's own decode and one integer compare — a junk record then costs
  what an honest one costs.
- **A venue adapter that hands out a malformed record collapses a walk that
  hashes before it verifies** to the genesis chain (a throw inside
  `answering`), putting the retired operator back in force for that reader.
  Verify-first is what keeps one bad record from un-doing every succession.
- **The sequencer's own walk cache earns its place** (deleting it costs ~14×
  on a still-clock door), and the rejected D1/D5 pre-filters, D3's venue-side
  verdict (the walk must not trust a venue; and `sync` is the memo's first
  customer anyway) are each a second mechanism for a property the memo owns.
- **Two defects live on main, found on the way**: `ErgoVenue.sync`'s first
  sync of any backing declaring a replacement rule threw its own `VenueError`
  (the frontier loop walks, the walk reads the clock, the clock refuses until
  `synced`, set after the loop — every Ergo test had re-synced an
  already-flagged view); and `ErgoVenue.replacementsFor` handed out its
  stored objects where the interface promises copies, so one reader
  overwriting a field rewrote succession for every later reader. Both fixed
  and tested ahead of the memo (`0938ddd`), with a double walk in `walkGap`
  threaded and a stale test comment corrected.

**The design, one sentence per piece:**

1. **One memo, in `replacement.ts` where the walk verifies**, held in a
   `WeakMap` on the venue OBJECT, keyed on the backing name AND the rule key,
   keeping the records it admitted — each with its hash — and the count of
   positions it has judged. The walk's first line becomes that call; so does
   `isNamedSuccessor`'s inline copy of the same admission rule (one mechanism
   for "which records count", where there were two).
2. **Verification stays first**, before the dedup, the tie, supersession and
   the exemption, and nothing unverified reaches `replacementHash`.
3. **Nothing else changes**: the sequencer's `(index, count)` cache, the
   `walked?` threading, `answering`, every walk answer (suite green, the seven
   slice-36 exploits byte-identical).

**What it costs, taken deliberately:**

- **The floor stays.** One strict-verify pair per record, once per venue
  object per process: ~10–12 s at 4,000 records on this machine, held open by
  the boot rule. Nothing that refuses to trust the venue goes below it, and
  the memo is empty at boot — persistence of verdicts across restarts is the
  one lever left, and there is no persistence layer to hang it on.
- **The memo leans on the Venue contract's append-only clause for WHO IS IN
  FORCE, not merely for freshness**: positions below `through` are never
  judged again for the life of the venue object, so a view that changed a
  record in place at the same length (out of contract: a reorganisation below
  the declared finality depth, or a third-party adapter) keeps seating an
  operator from a record the venue no longer holds, and no later append heals
  it. A view that SHRANK is re-judged from scratch. The per-record verdict
  memo removes that lean at 14× the per-walk cost; it is built
  (`scratch/panel37/security/vrepo`) and is the fallback if the clause is ever
  weakened.
- **The sequencer's cache key still decodes every record per door call** on
  the local venue (~6 ms at 4,000): the residual ×3.9 on a flooded door. A
  `replacementCountFor` Venue method makes it flat and was built (S+); it
  touches the interface for a constant factor and is deferred.

**The numbers after** (the same probes, this machine): live chain per block
**14.5 s → 35 ms**; a holder's grade 13.5 s → 3.8 ms; cold resume 56 s → 12 s
(the floor). Verifies per full round at 4,000 junk: 36,000 → 3,000, and those
are the new records, once.

**Three claims the build must carry as named tests, because the suite is
green without them:** the twin published first does not displace the signed
handover; a hand-built backing with the real name and another rule key does
not poison the real backing's walk; a malformed record from a venue drops
itself and not the walk. Plus the mechanism's own: a record is verified once
per venue view, and a view that shrinks is re-judged.

**Residues recorded, not built:** the verify cost itself (4–6 ms is 40–60×
what Ed25519 usually costs; if a faster path exists within "no other crypto
dependencies" it is worth more than any cache); the six `replacementsFor`
reads one door call makes (five of them the cache key); `ErgoVenue.sync`'s
frontier cost, unmeasured (needs a mock node); `ErgoVenue.publishedOpsFor`
and `revocationsFor` hand out stored objects too (the same copy-rule class as
the fixed accessor); `sync` never clears its own flag while re-gathering; the
rule-holder can make a record cost 9.5 ms rather than 3.5 (a valid first
signature), 2.6× a stranger's rate; and the fee model — on the local venue
the record count is unbounded, on Ergo it is a chain fee times N.

**Spec change:** none needed. §C2 says the record is witnessed and the
reader walks it; how often a reader verifies is the implementation's.

## 2026-09-02 — Panel: the walk — the book is what the record's descent reaches, the empty book is a signed claim, and currency is `serves`
